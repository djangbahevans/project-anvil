# Anvil design

Anvil is a native C++ code editor aimed at the VS Code workflow, with lower memory use and faster startup and input latency than an Electron application. It runs a subset of VS Code extensions in a separate Node.js process. Scope is defined in [ADR 0009](adr/0009-scope-and-non-goals.md); the rationale for each choice below is in the linked ADRs.

## Process model

```text
+---------------------------- anvil (C++/Qt 6) ----------------------------+
|  ui (Qt Widgets)                                                         |
|     |                                                                    |
|  workbench services: commands, config, workspace, language, terminal     |
|     |                         |                                          |
|  editor core            ext-host bridge  ---- pipe / socket ----+        |
|  (buffer, cursors,      (MainThread* services)                  |        |
|   layout, highlight)                                            |        |
|  platform (pty, fs watch, process)                              |        |
+-----------------------------------------------------------------|--------+
                                                                  |
      LSP servers, ripgrep, shells: child processes     +---------v--------+
                                                        | node: upstream   |
                                                        | extension host   |
                                                        +------------------+
```

- The editor is one native process. Extensions run in a separate Node process started on first use ([0004](adr/0004-extension-host-node-child-process.md)).
- Language servers, ripgrep and shells are child processes managed by the editor.

## Layers and dependency rule

Dependencies point downward only (`ui` → `workbench` → `exthost` → `core` / `platform`, each a CMake target that links only the ones below it). `search` depends on `core` and `platform` alone, so that `exthost` and the layers above it can use it. `core`, `workbench`, `search` and `platform` never include Qt GUI headers ([0003](adr/0003-ui-toolkit-qt6-widgets.md)).

| Layer | Responsibility |
| --- | --- |
| `ui` | Qt Widgets: the main window with a tab per open document, the editor view that paints a document and turns input into editing commands, the quick pick popup behind the command palette, and the bridge that runs the extension host from the event loop. |
| `workbench` | The editor layout (groups of tabs and the tree that arranges them), the store of the editor's state, and as they arrive commands, keybindings, configuration, workspace model, language-feature routing, terminal sessions. |
| `exthost` | Node process supervision and the C++ implementation of the `MainThread*` RPC services, including commands and the documents and editors that extensions see ([0005](adr/0005-reuse-upstream-extension-host.md)). |
| `search` | Finding ripgrep and listing the files of a folder with it ([0020](adr/0020-listing-workspace-files.md)). |
| `core` | Text buffer, undo, cursors and selections, search and replace, `when` expressions, line layout, highlighting, UTF-16 boundary conversion ([0006](adr/0006-editor-core-and-text-encoding.md), [0010](adr/0010-syntax-highlighting.md), [0013](adr/0013-pcre2-for-search.md)). |
| `platform` | Pseudo-terminals, file watching, process spawning, OS paths. The only layer with per-OS code ([0008](adr/0008-cross-platform-from-the-start.md)). |

## Editor core

`core::Text` is an immutable, persistent rope of UTF-8 chunks whose nodes cache byte, UTF-16 and newline counts; copying it is a snapshot. `core::TextBuffer` holds the current text and reports each edit as a `TextChange`. The text uses `\n` line breaks only. Positions exchanged with extensions and language servers are zero-based line and UTF-16 column, converted by `Text::position_at` and `Text::offset_at` ([0006](adr/0006-editor-core-and-text-encoding.md)).

`core::EditController` implements the editing commands (typing, deleting, motion, selection, undo, whole-line copy, cut and paste) on a document, for all cursors at once; the Qt editor view only paints and forwards input ([0012](adr/0012-editing-commands-in-core.md)). Home is VS Code's: it moves each caret to the first character of its line that is not a space or a tab, to the start of the line when the caret is already there or the line has no such character, and with Shift it extends the selection from the anchor (`Motion::home`; `Motion::line_start` is column 1 always). Copy, cut and paste with several cursors follow VS Code's `getPlainTextToCopy` and `_distributePasteToCursors`. `copied_text` gives one piece for each selection and one for the line of each caret (its text and a line break), in document order and once for carets on one line, and joins them with line breaks, so two carets on separate lines copy `one\n\nthree\n`; the pieces travel on in the clipboard's `application/x-anvil-editor-data` entry as `multicursorText`, and `isFromEmptySelection` stays true only for a lone caret. `delete_cut` removes the same ranges: selections and the lines of carets, the break before the last line of several unless the line before is cut as well, with ranges that overlap deleted as one. `paste` gives each cursor its own piece when the pieces are as many as the cursors; otherwise, text that is not a whole line and has as many lines as there are cursors, ignoring one line break at its end, goes one line to each; anything else is pasted at every cursor. The occurrence commands that create several cursors from the text follow VS Code's `multicursor.ts`. `EditController::occurrence_query` takes what to search for from the primary selection: the word at a caret (searched as a whole word with matching case when the caret is alone, with the find bar's options when it is not) or the selected text with the find bar's options, as plain text. `add_next_occurrence` adds the first match at or after the end of the primary selection, wrapping once around the text, and skips a match that overlaps a selection or touches a caret; the new selection is the primary one. `select_all_occurrences` replaces the selections with every match up to a limit, and the match that meets the primary selection stays primary. `EditorView` keeps the search that the first command made, whole words and case included, until the selections change by other means, the editor loses the focus or the find bar's options change; several selections of different text first grow their carets to words instead. The find bar owns the search when it is shown, has a pattern and the editor has no focus. Alt+Enter (`editor.action.selectAllMatches`, under the `findWidgetVisible` context key) selects the matches of the bar's own search, regular expression included.

`core::Document` adds selections, an undo history and the file format (line ending, byte order mark) to a buffer. Edits are applied as validated batches and reported as ordered change lists; undo steps hold forward and inverse replacements that share storage with the text, and edits can be joined into undo groups. The history keeps a bounded number of groups, 1000 by default ([0011](adr/0011-document-model.md)).

`core::Search` is a compiled query (literal, case, whole word, regular expression) with `find_next`, `find_previous`, `find_all` and replacement expansion. It reads a `Text` snapshot in bounded windows, so it never copies a whole document and can run on a worker thread; a stop token cancels it ([0013](adr/0013-pcre2-for-search.md)). `ui::FindBar` drives it: documents up to 1 MiB are searched at once, larger ones on a worker thread whose result is discarded when the document changes, and at most 20 000 matches are collected. Replace All is one `Document::apply_edits` call, so it is one undo step.

`core::WhenExpression` parses and evaluates VS Code `when` expressions, the conditions that decide whether a keybinding, menu item or command applies (`editorTextFocus && !editorReadonly`, `resourceExtname == .md`). `evaluate` reads a `core::ContextKeys`, a map from key to a boolean, number, string or list of strings, and an unset key is falsy. The syntax, the precedence and the JavaScript-style coercions of `==`, the comparisons and `=~` follow VS Code's `contextkey.ts`, so the `when` clauses of extensions behave as they do there; `=~` patterns are compiled with PCRE2 in the JavaScript-compatible mode that [0013](adr/0013-pcre2-for-search.md) uses for search. Parsing normalizes: `&&` is distributed over `||`, negation is pushed down to the keys, and terms are sorted and de-duplicated, so two spellings of the same expression have the same `canonical()` string and compare equal, which the keybinding resolver relies on. A parse error reports the byte offset of the problem. An expression is immutable and cheap to copy, so it can be evaluated from any thread.

`core::KeyChord` is a key binding as VS Code writes it in `keybindings.json`: one to four steps, each with modifiers (ctrl, shift, alt, meta) and a key. `parse_key_chord` reads `ctrl+k ctrl+c`, `cmd+shift+p` or `Ctrl-Shift-K` (any case, any order of the modifiers, `+` or `-`, `cmd`, `win` and `super` for meta, white space between steps) and fails with the position of an unknown key or modifier, a modifier without a key, an empty text or a fifth step, so two spellings of a chord are equal values. `format_key_chord` writes the lowercase form with meta as `cmd`, `win` or `meta` for the platform, and `key_chord_label` writes what the interface shows (`Ctrl+Shift+K`, `Super+K`, `⇧⌘K`, with arrows for the arrow keys on macOS). The keys are one generated table (`key_table.hpp`, from VS Code's `KeyCode`, with the lowercase name that key bindings use for a US keyboard, another name for some punctuation keys such as `oem_3` for the backquote, and the label) that parsing, formatting and, later, the translation of Qt key events read. A modifier that is also the key, as in `ctrl+ctrl`, is not held: the chord is the key `ctrl`. The tests replay about 1,500 strings that VS Code's own parser and label providers were run on (`tests/core/data/key_chord_cases.json`), apart from what the port does on purpose differently: `super`, tabs between steps, the limit of four steps, and keys named by position (`[KeyK]`).

`core::KeybindingTable` merges the key bindings of the editor, of extensions and of the user as `keybindingResolver.ts` does. A binding has a key chord, a command, an optional `when`, optional arguments and a source; the table orders them by source (built-in, extension, user) and then by the order they were given in, and a key press finds the last binding in that order whose first key is the press and whose `when` holds in the context keys. That binding decides everything, so a binding that is also the start of a longer one waits for the next key if the longer one comes later and runs if it comes first. `resolve(pending, next, context)` answers that nothing is bound, that more keys are needed, or the command with its arguments and whether the press should also reach the widgets (a command written with a leading `^`). A command written with a leading `-` removes the built-in and extension bindings of that command whose key starts with the key of the removal (every key without one) and whose `when` implies the removal's; the user's own bindings and bindings whose `when` is `false` are never in the table. `lookup` and `lookup_primary` give the bindings of a command for menus, leaving out a binding that a later one for the same key covers completely. `WhenExpression::implies` is VS Code's proof on the normalized expressions, which finds less than there is to find. `read_keybindings` reads the array of a `keybindings.json`, reports each entry it cannot use with its position and skips it. `core::KeyDispatcher` is the state of the dispatch: the presses of a chord in progress and the time of the last one. A bound key runs its command and is handled; the first key of a chord waits and tells the interface what to say ("(Ctrl+K) was pressed. Waiting for second key of chord..."); a key that continues no chord ends it with "The key combination (Ctrl+K, Backspace) is not a command." and is swallowed, so Escape cancels a chord without reaching the editor; a chord that is not continued for five seconds, or when the window loses the focus, ends silently; a modifier alone changes nothing. The time is a parameter, so the tests move a clock by hand. The tests replay 3,200 key presses on 200 random tables, their lookups for menus and 1,500 pairs of `when` expressions against what VS Code's own resolver does (`tests/core/data/keybinding_cases.json`). Left out: keys named by position, a binding for one platform in `keybindings.json` (`mac`, `win`, `linux`), and chords of a single modifier such as `shift shift`.

`core::LanguageRegistry` gives a file its language id as VS Code's `languagesAssociations.ts` does. `add` takes a language contribution (the `id`, `aliases`, `extensions`, `filenames`, `filenamePatterns`, `firstLine` and `mimetypes` of an extension manifest) in registration order, and contributions with one id merge into one `Language` with its name (the first alias, the id when there is none, nothing for an empty list). `language_for(path, first_line)` takes the path with forward slashes, lower-cases it (ASCII only) and tries, in order: the user's associations (`files.associations`, set with `set_user_associations`, which match by glob against the file name, or the whole path when the pattern contains `/`), then the registered rules, where an exact file name beats a file name pattern and a pattern beats an extension (the end of the file name, so `.d.ts` is one), and then, only when none of these matched, the first line against the registered `firstLine` expressions. Among the rules of one kind the longest pattern or extension wins and, among equal ones, the contribution registered last. A byte order mark in front of the first line is ignored, an empty path has no language and the first line is not read for it, and a language that nothing gives, or that is not registered (a user association of an unknown id), is `plaintext`. First line expressions are ECMAScript regular expressions compiled with PCRE2 in UTF mode, with `^` put in front of those that do not start with it, as VS Code does; one that does not compile, or that matches the empty string (apart from `^`, `^$` and `^\s*$`), is skipped and `add` returns the reason. `LanguageRegistry::with_builtin_languages()` registers the generated table `language_table.hpp` (`scripts/generate-languages.mjs`): `plaintext` and the languages of VS Code's built-in extensions, in the order the extension scanner loads them. The tests replay about 8,000 paths and first lines that VS Code's own `LanguageService` was run on, with and without user associations (`tests/core/data/language_cases.json`, from `scripts/generate-language-cases.mjs`), and compare the merged languages. Not modeled: the `configuration` file that puts a contribution's extensions first in a language's list of extensions, and the Unicode case folding of non-ASCII letters.

`core::ColorTheme` loads a VS Code color theme: the workbench colors and the token color rules of a theme file and of the files it includes (`dark_modern.json` includes `dark_plus.json`, which includes `dark_vs.json`), following `colorThemeData.ts`. An included file is applied first and the including file on top, so the including file's colors win and its token rules come later; `colors` maps a workbench color key to `#rgb`, `#rgba`, `#rrggbb` or `#rrggbbaa`, the value `"default"` removes a key an included file set, a value that is not a string is ignored, and a string that is not a color is skipped with a warning. The token rules stay the JSON that was written, for the scope matcher. The file is JSON with comments, found through a loader function so that `core` does no file I/O, includes are relative to the file that names them (up to 16 deep, with cycles and missing files reported with the chain of files), and a theme's kind (dark, light, high contrast) comes from the contributing manifest's `uiTheme`. A `tokenColors` that names a TextMate file, the legacy `settings` array and an include that is not a `.json` file are errors; `semanticTokenColors` is ignored.

`core::TokenTheme` styles the tokens a highlighter produces from the `tokenColors` rules of a theme, as VS Code does for TextMate tokens (`vscode-textmate`'s theme). A rule's scope is comma-separated selectors, an array of them, or absent (the default style); a selector is words separated by one space, the last naming the scope of the token and the rest, in order and not necessarily adjacent, its ancestors, with `>` asking for the very next one; a word names a scope when it equals it or is a prefix that ends at a `.`. The more specific rule wins (more segments in its scope, then longer ancestor words, then more ancestors), a later rule of the same scope wins a tie, and a rule leaves the fields it does not set to the rules of shorter scopes. The style of a token is the default style with the matching rule of each scope of its stack applied from the outermost to the innermost, so a scope with no rule shows what its enclosing scopes gave it. `style_for` takes the scope names as views and does not allocate; 1,000,000 lookups over Dark+ take about 0.14 s. Where the tokenizer paints black on white when a theme has no default rule, the unset fields are left for the editor's colors. `tests/core/data/token_theme_cases.json` holds styles recorded from the real tokenizer (`scripts/generate-token-theme-cases.mjs`), which the tests replay.

`core::Highlighter` is what a syntax highlighter tells the editor ([0010](adr/0010-syntax-highlighting.md)): `spans(line)` gives the spans of a line (UTF-16 columns, sorted, not overlapping, the innermost scope winning) with TextMate-style scope names, `root_scope()` the scope of the language as a whole and `version()` a number that changes when the spans can differ. How the spans are found is the implementation's: tree-sitter is the first and a TextMate tokenizer can be another. `EditorView::set_highlighter` takes one; the view asks it for the lines it lays out, which are the lines in view and the line of the caret, and gives each span the style that the theme's `tokenColors` (`core::TokenTheme`, which `ThemeStore` builds from `ColorTheme::token_colors()` and hands to the views through `WorkbenchColors::token_theme`, so that a theme change repaints them once) gives the scope stack `{root scope, span scope}`: the foreground, the background and the font style. The formats are set on the `QTextLayout` before it is laid out, because only then do bold and italic apply. A selection changes the background of the selected text and leaves its syntax color, as in VS Code, so with a theme the selection sets no foreground. Text outside every span, and a rule with no color, keep the editor's foreground. `refresh_highlighting` repaints the view when the highlighter's version has changed since the last paint, which is how an asynchronous highlighter says that spans arrived.

`core::TreeSitterHighlighter` is the tree-sitter implementation, built when `.deps/tree-sitter` exists (`scripts/fetch-tree-sitter.sh`, which pins the runtime and the grammars by archive hash; `ANVIL_TREE_SITTER` is defined for everything that links `anvil_core`). It parses a `Text` snapshot when it is made, with a `TSInput` that reads the snapshot's storage chunks (`Text::chunk_at`) without copying the text, and answers `spans(line)` by running the grammar's `highlights.scm` on the byte range of that line. The query cursor returns captures in document order, nested and sometimes with equal ranges; one pass with a stack turns them into the spans of the interface: the innermost capture of a stretch wins, and of captures with the same range the pattern that comes first in the query. Byte columns of the parser are converted to UTF-16 columns of the line. Each capture name goes through a per-grammar table (`core::CaptureScope`, `capture_scopes.cpp`) to a TextMate-style scope: the row with the longest capture name that equals the name or is a prefix of it ending at a `.` gives the scope, and a capture without a row has none, so its text keeps the style of the enclosing capture. The grammar's query is embedded in the library when it is built. `apply` follows an edit: it rebuilds each change's `TSInputEdit` with byte columns from the highlighter's own text (a `DocumentChange` lists its changes against the texts the ones before left, and the highlighter replays them), edits the tree, and parses again with the old tree, which reads only the bytes the edit reached. `spans` runs the query for the line it is asked for, every time: the window reads snapshots (below), which keep what they were asked for until the next edit makes a new one, so a highlighter does not keep the spans of lines. A model-based test applies random edits to documents of each language and compares every line, and the whole tree, with a fresh highlighter after each. The test of the cost counts the bytes the parser asks for, which is deterministic, and requires the reparse to read at least 50 times fewer than the first parse; a second test compares processor time on a document of 15,000 members, below. `bench/highlighter_bench.cpp` measures a document of nested objects and one of a single object with 70,000 members.

The runtime that `scripts/fetch-tree-sitter.sh` pins is a commit of the 0.28 development line (`d63dc4a`, after release 0.27.2), and not a release. With release 0.27.2 an edit of one character in the middle of the object with 70,000 members (5 MB) took about 180 ms: 47 to 85 ms in the parse with the old tree, 55 ms in `ts_tree_get_changed_ranges`, and 6 to 10 ms to free the old tree. The parse is that long because the release marks the reductions of a repetition (the members of an object, the items of a list, the top-level declarations of a file) as fragile, which makes a reduction not reusable: the parser shifts, and reduces, each of the 71,000 members one by one instead of reusing the balanced subtrees of the old tree (the debug log of the parser says `reuse` about 70,000 times for one edit), so an edit costs time in proportion to the number of siblings, and both the parse and the comparison of the trees grow with them (5,000 members: 3 ms; 20,000: 15 ms; 80,000: 160 ms). The fix is upstream commit `84cdfbc` ("don't mark repetition reductions as fragile"), with the fixes of reuse that followed it, and is in no release yet; with it the same edit reuses 22 to 34 nodes and the parse takes 10 to 70 microseconds. Measured as candidates, on the document of 70,000 members (release build, WSL2): leaving out the comparison of the trees, which the window does not need because no one reads the spans of the worker's highlighter, saves 55 ms of 180, and for a language without inline content `apply` no longer does it; parsing off the typing path (the worker) hides the whole cost from typing, at 150 ms from an edit to the colors of what was typed, which is the number that `WorkerRoundTrip` measured with release 0.27.2; the pinned commit makes the reparse 25 microseconds and the worker's round trip 0.16 ms, 7,000 times and 900 times less. A commit that is not a release is a risk that a release is not: it has had few users, and the history after 0.27.2 is long. The grammars, the golden files and the model tests of all eight languages, and the run of the whole suite under AddressSanitizer, are what stands for it, and moving to release 0.28 when it comes is a change of the line in the script. The fetch script unpacks with `tar -m`: a pin that changes must have files newer than the objects built from the ones it replaces, or the build keeps the old runtime, as the times that the archive stores are older than the objects.

Text predicates of a query (`#eq?`, `#match?`) are not evaluated by the query cursor; a grammar whose highlights use them needs that implemented first. [docs/howto/adding-a-grammar.md](howto/adding-a-grammar.md) lists the steps for a language.

A language's query is made of Anvil's own patterns (`src/core/queries/<name>.scm`) followed by the `highlights.scm` files of its grammars; the first pattern wins when two capture the same node, so Anvil's decide the nodes they name, and a language that builds on another (C++ on C, TypeScript on JavaScript) has its patterns before those it takes from it. A capture can be weak in the table (`variable` and `property` of JavaScript): it gives way to any other capture of the same node whatever the order, which is what the grammar's `(identifier) @variable` placed before its function patterns needs. The scopes of the tables carry no language suffix; the grammar of a language adds it (`json`, `c`, `cpp`, `js`, `js.jsx`, `ts`, `tsx`), so that JavaScript, TypeScript and TSX share rows, and JavaScript React has the JavaScript grammar with its own root scope. The Anvil patterns exist because the grammars' queries capture every keyword as `@keyword`, where the scopes of VS Code's grammars (and so the colors of its themes) tell `keyword.control` from `storage.modifier` from `storage.type`; C and C++ are written against the scope names of VS Code's own grammars and checked by eye in Dark Modern and Light Modern. A capture without a row in the table (`variable` and `delimiter` for C and C++) has no scope and, being dropped before two captures of one node are compared, does not hide a more specific one. The query cursor leaves the text predicates of a query to the caller: `#match?` and `#not-match?` are evaluated with PCRE2 on the captured text, `#eq?` and `#not-eq?` compare it, `#is-not? local` holds and `#is? local` does not (no local variables are tracked, so a local variable called `console` is colored as the global one), and a query with another predicate is refused when the highlighter is made. A grammar's compiled query is built once for the process and shared by every highlighter and snapshot of the language, since compiling that of C++ takes longer than parsing a small file. The C++ parser is the largest part: its object file is 3.4 MB and compiling it takes about 2.5 s and 400 MB of memory in a release build; C's is 0.65 MB.

Markdown has two grammars, one for the structure of a document and one for what is inside a paragraph, a heading or a table cell, and the first leaves the second the `inline` and `pipe_table_cell` nodes of its tree. For a grammar that has an inline grammar, `TreeSitterHighlighter` finds those nodes after each parse of the block tree and parses each with the inline grammar as a text of its own: the text of the node without the named nodes inside it, which are the marks that the block grammar owns (the `>` that begins each line of a quoted paragraph), with a table of the pieces that maps an offset of that text back to the document. Parsing the text apart from the document makes a tree independent of where the node is, so the trees are kept by their text and a node whose text has not changed keeps its tree, whatever happened above it, and an edit parses again only the paragraphs it reached; After an edit only the inline nodes near it are looked at: `apply` keeps the range that the edits and the ranges of `ts_tree_get_changed_ranges` (which it compares only for a language that has inline content) can have touched, as one range of the new text (each edit moves what lies after it and adds its own range), walks the block tree only through the nodes that touch it, and takes the nodes of the last parse that lie before the range as they are and those after it with their offsets moved by the change in the size of the text. The pieces of a node are counted from its beginning, so a moved node keeps them, and a node is two shared pointers, so the copy of the layer that each edit makes (the snapshots share the last one, which must not change) allocates nothing per node. The trees by text are pruned when they are twice the nodes of the document. The tree of a node is not edited, because a paragraph is small and has no need of incremental parsing. A test counts the nodes looked at (`inline_nodes_visited`): an edit at the start, the middle and the end of a document of 3,000 paragraphs looks at no more than a few. The spans of a line are the captures of the block tree and of every inline tree that overlaps the line, which `flatten` sorts out as for one tree, the inline capture winning where both capture the same text. The inline trees are shared with the snapshots, which only read them. A span has one scope and not the stack that a TextMate grammar gives a token, so the marks that VS Code scopes inside a heading (`#`) have the scope of the heading, and the delimiters of emphasis have no scope of their own and keep that of the emphasis around them; the code in fenced blocks is not parsed (the injection of the languages named in the info string is not implemented). Adjacent spans of the same scope are one span. On a document of about 1 MB with 9,000 sections and 18,000 paragraphs and list items (`MarkdownFirstParse` and `MarkdownReparseAfterOneCharacter` in `bench/highlighter_bench.cpp`; release build, WSL2), the first parse takes about 1.5 s and the reparse after an edit of one character about 15 ms, finding the inline nodes again being a few milliseconds of it. A document of 50 KB takes a twentieth of that. (With release 0.27.2 the reparse took 310 ms, the block tree having the cost of many siblings described above.) The block parse of a worker runs off the typing path.

The editor does not parse on its UI thread. `core::HighlightWorker` owns a `TreeSitterHighlighter` and runs it on a `std::jthread` per document: the first parse, then the edits that `DocumentChange`s describe, which it queues together with the snapshot of the text after each. While a parse runs, further edits are coalesced (their changes concatenated, only the latest text kept) into one incremental parse afterwards, so a burst of typing costs one parse after it. A change whose version does not follow the previous one by one is an edit nobody reported, and the worker parses the latest text from scratch instead of trusting its tree. After each parse the worker hands over `TreeSitterHighlighter::snapshot()`: the text and a copy of the tree (`ts_tree_copy` shares the nodes and is safe to use while the worker edits its own tree) with the query data, which is read only, as a `Highlighter` that the UI thread queries line by line (the spans of a line are cached in the snapshot). A result is not handed over when a later edit is already queued, and stopping the worker (document closed, language changed) cancels a parse in progress through the progress callback of the parser and joins the thread, so a 5 MiB parse does not hold up closing the tab.

`ui::Highlighting` holds a worker and a `core::LiveHighlighter` for each open document whose language has a grammar (`TreeSitterHighlighter::supports`), made when a view first shows the document, and reports results to the window through a queued call, so `LiveHighlighter` is only touched on the UI thread. The window reports every change of a document's text to it (`MainWindow::highlight_edit`: edits typed in a view, applied by extensions, restored on reopening a closed editor and made by saving). `LiveHighlighter` takes a result only when it is for the document's current version: a result for an older version is dropped, because the worker is already parsing a later one. Until a result for the current version arrives, `spans(line)` maps the line back through the edits made since (each edit is the first row and the numbers of rows before and after) to the line of the result it came from, so the lines below a new line keep their colors and an edited line keeps the colors it had, rather than flashing plain. Changing the language of a document (the picker, an association, Save As to another name) gives the views the highlighter of the new language, or none, and stops the old worker. When spans arrive, `EditorView::refresh_highlighting` compares a digest of the spans of each line in view with the digest of what it last laid out and repaints only the lines that differ.

A document of more than `core::max_highlighted_bytes` (5 MiB) is not highlighted, and a document that grows past it loses its highlighter; one that shrinks below it is highlighted again the next time a view shows it. A line of more than `core::max_highlighted_line_units` (10,000 UTF-16 units) has no spans. The first parse of a 5 MB document takes about 0.6 s and runs on the worker's thread. From an edit of one character to the worker's result for it takes about 0.2 ms on a document of nested objects and as much on one object with 70,000 members (`WorkerRoundTrip` in `bench/highlighter_bench.cpp`; release build, WSL2); typing itself does the same work as for a plain document plus queueing the change, which `TypingInAHighlightedDocumentCostsAboutWhatItDoesInAPlainOne` checks with 200 and 20,000 lines.

`EditorView` keeps the `QTextLayout` of the lines it has laid out, so that a paint, a caret blink, a hit test or a scroll reuses them: a map from line number to layout, the least recently used quarter dropped when it holds more than 256 layouts or twice the lines in view. A layout depends on the text of its line, the font, the tab size, the control character setting and the syntax formats, and the cache is kept exact: an edit (`apply`, which has the `TextChange`s) drops the layouts of the replaced lines and moves the layouts below to their new line numbers, so typing lays out only the line typed on; a different document version (which an edit through another view or by an extension causes, and is checked at each lookup), `set_document`, a new font (which `apply_settings` also causes for the zoom and the font size), a tab size, a control character setting, a new highlighter and a change of the workbench colors drop everything; `refresh_highlighting` drops the layouts in view whose spans changed, and those out of view that were made from spans, as they are made again on the next paint. Selections, find highlights and the symbols of control characters are formats given when a layout is drawn, so they are not part of the cache. `EditorView::layouts_built()` counts the layouts made, which is what tests assert instead of the time.

Lines of the editor are as far apart as in VS Code, 1.35 times the font size (19 pixels at 14) and 1.5 times on macOS (`EditorDefaults::line_height_ratio`), with the text in the middle, and further for a font whose laid out line or underscore needs more room. `editor.lineHeight` is not read. The backgrounds of selections, find matches and control characters are filled to the whole height of the line before the text is drawn, and the `QTextLayout` is given only colors of text: it redraws what it has a format for inside the height of the text, which cuts off an underscore that a font draws below it. With the app's themes, which set the background of the selection, selected text keeps its color and nothing is redrawn.

Scroll positions are in pixels. The wheel scrolls as VS Code's scrollable element does: `core::wheel_scroll` turns the notches of a wheel event (touchpads report angles too), Alt, Shift and the settings `editor.mouseWheelScrollSensitivity`, `editor.fastScrollSensitivity` and `editor.scrollPredominantAxis` into pixels, and `EditorView` accepts every wheel event over its text, so that nothing around it scrolls. The X11 and Windows plugins of Qt swap the axes of an event while Alt is held, which `ui::wheel_turn` undoes. The scroll bars keep Qt's own wheel behavior. The vertical range ends with the last line at the top, or with `editor.scrollBeyondLastLine` off at the bottom. The horizontal range ends `editor.scrollBeyondLastColumn` characters after the widest line measured, with room for a caret at least; where lines wrap at the width of the view the setting does not apply.

The scroll bars of the editor and of the quick pick's list are `ui::ScrollBar`, a `QScrollBar` that paints and handles the mouse itself, to look and behave as VS Code's: no arrow buttons, a slider of the length that the shown part of the content has to the whole, at least 20 pixels, in `scrollbarSlider.background`, `.hoverBackground` under the pointer and `.activeBackground` while dragged, and a press on the track that brings the middle of the slider to the pointer and drags from there. They are 14 pixels wide and 12 high in the editor and 10 wide in the list. A bar keeps its space beside the content and does not overlay it or fade out, so that the layout of the views does not depend on it; it therefore paints the color of the content (`editor.background`, `quickInput.background`) below the track, and `scrollbar.background` over that when a theme sets it. The slider colors are those of VS Code's registry where a theme leaves them out, derived from `contrastBorder` in high contrast themes (`ThemeStore`), and the default theme does not stand in for them. The keyboard and the wheel on a bar are Qt's. The Explorer has the platform's scroll bars.

A line is laid out by `ui::ChunkedLine` as consecutive chunks of about 2048 UTF-16 units, each a `QTextLayout` of its own, that read as one line, so that showing a part of a line of a million characters costs as much as showing that part of a short one; a line no longer than a chunk is one layout. A chunk is cut at a boundary between grapheme clusters, and never inside a surrogate pair. Only the chunks that intersect the view, the caret or a point that is hit-tested are laid out, at most sixteen of a line are kept, and the width of every measured chunk stays. A chunk that has not been laid out has an estimated width, the advance of an `M` for each unit and tabs to their stops, which is exact for a monospace font without wide characters; the x of a chunk is the sum of the widths before it, and the horizontal scroll range follows from the same sums. Tab stops are measured from the start of the line: a chunk that starts between two stops is given the line's stops as a tab array, shifted by where it starts. `ensure_cursor_visible` lays out the chunks that are going to be on screen before it scrolls, because their measured widths can move the caret. When a long line is edited, or its highlighting changes, its new layout takes the widths of the chunks before the change from the old one, so that the text on screen does not move while typing in a line of wide characters. The paint gives each line formats (selections, find highlights, control characters, whitespace marks) only for the columns that are shown. Two things differ from one layout of the whole line: right-to-left text reorders within a chunk only, and a proportional font can kern the two characters at a cut apart by less than a pixel. Lines of more than `core::max_highlighted_line_units` have no syntax colors.

`EditorView` draws a mark for the spaces and tabs that `editor.renderWhitespace` asks for, and shows control characters as symbols. `core::whitespace_columns` decides which columns get a mark with VS Code's rules for `boundary`, `selection`, `trailing` and `all` (it is tested against a port of the loop of `viewLineRenderer.ts` for every short line over space, tab and a letter); the view draws a middle dot for a space and a right arrow for a tab in the cell of the column, in `editorWhitespace.foreground`, and finds the first visible mark by bisection, so a long line costs what its visible part costs. A control character below U+0020 other than a tab, and U+007F, is replaced in the laid-out text by its symbol of the Control Pictures block (one column each, so columns are unchanged) and drawn white on `rgb(150, 0, 0)`, as VS Code does; `editor.renderControlCharacters` turns that off. The commands `editor.action.renderWhitespace.*` and `editor.action.toggleRenderControlCharacter` change the two settings with `MainWindow::change_setting`, and View > Appearance shows the mode with a check mark. Directional formatting characters, which VS Code shows as `[U+202A]`, are left as they are.

The mouse follows `viewController.ts` of VS Code. The modifier that `editor.multiCursorModifier` names (Alt, or Ctrl, which is Cmd on macOS) makes a click add a cursor, and dragging then extends that cursor; with another modifier pressed as well the click does nothing. Shift with the modifier, and Shift+Alt when the modifier is Ctrl, selects a rectangle that grows from where the primary selection began, so that Shift+Alt+click extends it. While `editor.columnSelection` is on, or Alt is held while dragging with Ctrl as the modifier, a drag selects a rectangle from the press. A rectangle has one selection per line between the press and the pointer, from the column under the first to the column under the second on each line, so a line that is shorter gets an empty or shorter selection at its end; the selection of the line of the pointer is the primary one. The rectangle is found from pixels (`LineLayout::column_at` of each line), so it is the one the user sees with tabs and wide characters, and `EditController::select_ranges` makes it the selections. `multiCursorModifier` is a context key with the values `ctrlCmd` and `altKey`, as in VS Code; its default is `altKey` because the setting defaults to `alt`. `editor.action.toggleColumnSelection` and `workbench.action.toggleMultiCursorModifier` change the two settings with `MainWindow::change_setting`; the menu shows the first as a check mark and offers the opposite modifier in the second. Column selection with the keyboard (Shift+Alt+arrows) is not implemented.

Up, Down, page movement and the cursors added above and below keep the *visible column*, VS Code's `CursorColumns` (`core::visible_column` and `offset_at_visible_column`): a tab goes to the next tab stop of `editor.tabSize`, and every other grapheme cluster counts one column, or two when its first code point is a full-width character or an emoji. A column inside a tab or a wide character goes to the nearer side, the earlier one when both are as near. A lone caret remembers its visible column across shorter lines, until it moves another way or is at the start or end of the text and moves further that way; several carets each aim for the column they are at. The clusters are split with VS Code's own rules and table (`src/core/grapheme_table.hpp`, written by `scripts/generate-grapheme-table.mjs`), which decide the same on every platform and treat two code points at a time; PCRE2's `\X` depends on the version installed, and 10.42 joins two emoji that follow each other. Left, right and delete still go by code points. Tab inserts spaces up to the next tab stop of the visible column. `tests/core/visible_column_test.cpp` compares the columns and the motions with records made from VS Code (`scripts/generate-cursor-column-cases.mjs`).

Word wrap shows a line on several rows ([0018](adr/0018-word-wrap-by-rows.md)). `core::break_line` gives where the rows of a line begin as VS Code's `monospaceLineBreaksComputer.ts` does with `wrappingStrategy: "simple"`, its default break characters and `wrappingIndent: "same"`: widths are counted in columns (a tab to the next stop, a full-width character the width that the caller measured, a character outside the basic plane two), a row ends before or after a break character or beside an ideograph, and where there is no such place it ends where the row is full; the rows after the first are indented like the line. Results are compared with records from VS Code (`scripts/generate-line-break-cases.mjs`). VS Code re-wraps with a second routine when only the width changes, which can break a line elsewhere; Anvil has the one routine, so the rows depend on the text and the options alone. A line that cannot reach the column, whatever its characters, is not examined. `core::RowMap` keeps the number of rows of each line, with the first row of every 256th line summed when a lookup needs it, and `apply` computes only the lines that a `DocumentChange` touched. In a release build, the map of 100,000 lines of source code takes about 11 ms and of a million about 100 ms, 100,000 lines that all wrap take about 80 ms, an edit that adds a line to a million-line map about 0.1 ms, and the rows of one line of a million characters about 5 ms (`bench/wrap_bench.cpp`, WSL2).

`EditorView::set_wrapping` wraps at the width of the view (the number of advances of `M` that fit the text area, with room for the caret), at a column, or at the smaller of the two. `MainWindow` decides it for each document from `editor.wordWrap` and `editor.wordWrapColumn`, and `EditorArea` gives it to every view that shows the document, together with the document when a view shows another one. View > Word Wrap (`editor.action.toggleWordWrap`, Alt+Z) works as VS Code's `toggleWordWrap.ts`: it overrides the setting for the current document, wrapped at the width of the view or not at all, and the next use removes the override. The override is kept in memory until the document is closed, and the setting is not written. VS Code's Markdown extension turns wrapping on for Markdown with a language-specific default, which Anvil does not read. The context keys `canToggleWordWrap` and `editorWordWrap` enable and check the menu item. The view then counts in rows where it counts in lines without wrapping: the vertical scroll range, painting, hit testing, the column selection with the mouse, scrolling to the caret and the line numbers, which show on the first row of a line, while the current line highlight covers all its rows. A line is shown by a `ui::LineLayout`, which lays out each row as a `ChunkedLine` when something first asks about it and keeps at most 256, so a line of a million characters costs the rows in view. The indent of the later rows is as wide as the leading blanks of the first, and their tab stops are those of the line: `LineBreaks::columns` says at which column each row begins. Where a line breaks, an offset is both the end of one row and the start of the next, and a caret is on the later row unless End, vertical movement, a click or a column selection put it at the end of the earlier one; selections stay offsets. The vertical scroll bar of wrapped text is always shown, because its coming and going would change the width that the rows are made for, and the horizontal one has a range only for a row wider than the view.

`EditController` asks its view for the rows (`set_row_source`) and then moves by them, as VS Code moves over its view lines (`core/row_motion`). Up, Down and page movement keep the visible column of the row, counted with the indent of a later row as spaces and tab stops from the start of the row; a column inside the indent is the start of the row. Home on a later row goes to the first character of the row that is not a space or a tab, and from there, or on the first row, does what it does on a line; End goes to the end of the row, and from there to the end of the line. The controller keeps which of its carets are at the end of a row (`ends_row`) for as long as the selections and the text are the ones it left, so another view of the same selections shows them at the start of the next row. Adding a cursor above or below goes by lines of the document, since `insertCursorAbove` and `insertCursorBelow` of VS Code do by default, and so do the commands that work on lines.

The row map belongs to the view, since two views of one document can wrap at different widths. It is made when the width, the font, the tab size or the zoom change, and when the line numbers gain a digit; the text at the top of the view stays at the top. An edit updates it from its `DocumentChange`: the view's own edits, those of another view of the document (`MainWindow::on_text_changed` tells the other groups, which also paints them again) and those of extensions pass the change on with `document_changed_elsewhere`. A view that has missed a version computes its rows anew.

View > Explorer (`workbench.view.explorer`, Ctrl+Shift+E) shows the Explorer in the side bar and gives it the keyboard focus, on the tree, or on the Open Folder button with no folder; used while the Explorer has the focus, it gives it back to the editor, as the command of a view container does in VS Code.

`MainWindow::save_all` (`saveAll`) writes every document with unsaved changes and a file, and asks for a name for each untitled one, in the order of the tabs of the groups; the documents are collected first and found again by identity (`uri_of`) before each is written, because a question runs a nested event loop in which extensions can close, rename or save documents. Cancelling a question stops the rest; a write that fails shows its error and the others go on. `MainWindow::revert` (`workbench.action.files.revert`) reads the file of the shown document again and replaces the whole text with it as one edit that undo can take back, moving each selection to its line and column in the new text, clamped to its end. The extension host is told of the change and of the save, and the document is clean. An untitled document is left alone, and a file that cannot be read or decoded leaves the document as it is and says so in the status bar. Revert File is enabled for a document with a file (`activeEditorCanRevert`, set for the menus); Save All is enabled while some document has unsaved changes (`dirtyWorkingCopies`). VS Code binds Save All to Ctrl+K S on Windows and Cmd+Alt+S on macOS, and Revert File to nothing.

`EditController::move_lines`, `copy_lines` and `duplicate_selection` (`editor.action.moveLinesUpAction`, `copyLinesDownAction`, `duplicateSelection`, ...) work on the lines that each selection touches, with VS Code's rules from `moveLinesCommand.ts`, `copyLinesCommand.ts` and `linesOperations.ts`: a selection of several lines that ends at the start of a line does not touch that line; a move swaps the block with the line next to it, so the selections keep their line and column, and nothing moves past the first or the last line (for a move down, the last line is the one where the selection ends, even when that end is at the start of the line); a copy puts the lines above or below the originals, and the selections stay on the original text, which is the upper copy when copying up and the lower one when copying down; Duplicate Selection copies the text of a selection after itself and selects the copy, and a caret copies its line down. Each command is one `Document::apply_edits`, so one undo step, and with several cursors every selection works on its own lines: when two moves would swap a line in common, the later selection is dropped, and when two copies would copy the same line, the earlier selection copies it (VS Code compares a selection with the first one and with the winners of earlier conflicts, which misses a pair of neighbors that come later; this compares it with the last selection that copies). The languages of VS Code can re-indent a moved line; with no languages there is nothing to re-indent. The model-based test `LineOperationsModel` compares the commands with a naive reference on arrays of lines for random documents, selections and cursor counts, and `copy_lines`/`move_lines` also agree with the cases of VS Code's own tests, which `CopyLines`, `MoveLines` and `DuplicateSelection` state.

`EditController::add_cursors_vertically` (`editor.action.insertCursorAbove` and `insertCursorBelow`) adds, for every selection, a copy of it one line up or down, with `cursorMoveOperations.ts`'s rules: each end of the copy goes to the column that end wants, which is a visible column as for the arrow keys, and on a shorter line it stops at the end of the line and remembers what it lacks, so that the next cursor added over a longer line is back at its column; the controller keeps that remembered width for the selections it made until they change. At the first line (up) or the last (down) the copy is the selection, so nothing is added. The first selection stays primary. `add_cursors_to_line_ends` (`insertCursorAtEndOfEachLineSelected`) replaces the selections with a caret at the end of each line they cover, except the last unless the selection ends inside it, and does nothing when no selection covers more than a caret. `add_previous_occurrence` (`addSelectionToPreviousFindMatch`) mirrors `add_next_occurrence`: it adds the last match that begins before the primary selection and overlaps no selection, wrapping from the end of the text, and `EditorView` shares the session that the two commands keep, so that the first press selects the word at a caret as it does for the next occurrence. VS Code binds Shift+Alt+Up/Down (with Ctrl+Shift+Up/Down as second keys) on Linux and Ctrl+Alt+Up/Down (Cmd on macOS) elsewhere to the cursors above and below, Shift+Alt+I to the line ends, and nothing to the previous occurrence.

`workbench::EditorLayout` moves between tabs and groups with VS Code's rules. `next_editor(forward)` (`workbench.action.nextEditor` and `previousEditor`) shows the tab beside the active one in the focused group, and past its end the first tab of the next group that has tabs (the last tab of the previous group), going around the groups and ending at the focused one; `next_editor_in_group` wraps inside the focused group. `navigate_recent(older, in_group)` (`openNextRecentlyUsedEditor`, `openPreviousRecentlyUsedEditor` and the `InGroup` pair) walks a history of use without showing a list: the history is taken when the first of these calls starts, as the tabs of the groups with the group that had the focus last first and each group's tabs from the most recently active (only the focused group's for `in_group`), and it is kept while the calls follow each other, because the layout ends it when the tabs or the focus change by anything else; each call moves one step in it and stops at its ends. The layout keeps which groups had the focus last (`groups_by_recency`, not saved). `neighbor(group, direction)` (`focusLeftGroup` and the others) computes where the tree puts each group (the ratios of the splitters give each a box), takes the groups that touch the edge of the group on that side and share more than a point of it, wraps to the opposite edge of the area when the group is at the edge (a lone group is its own neighbor, so that nothing happens), and chooses the one that had the focus last when several touch. `MainWindow` focuses the nth group in the order shown for `focusFirstEditorGroup` to `focusEighthEditorGroup`; the group after the last one is made by splitting the last one to the right, as VS Code does, and a further one does nothing. The Go menu offers these, and VS Code's Ctrl+Tab list that it shows while Ctrl is held is left out.

`workbench::NavigationHistory` is the list of places behind Go > Back, Forward and Last Edit Location (`workbench.action.navigateBack`, `navigateForward`, `navigateToLastEditLocation`), with the rules of VS Code's editor navigation stack. A place is a group, a document and the primary selection as lines and columns. `NavigationStack` keeps the places in the order they were visited and the one the user is at: a new place is added after the current one and drops the places ahead of it, unless the user is in the same editor of the same group within 10 lines of the last place, in which case it replaces the current entry, so moving the caret about one area of a file makes one entry. A navigation (a place the user chose to go to) is added even within 10 lines unless it is on the same line. Activating another editor or another group adds a place. At most 50 places are kept; the oldest go first, and places that become the same after a removal merge. The history has two stacks: every place the user has been, which Back and Forward walk, and the places where the text was edited, from which Last Edit Location takes the newest; going there is also a place in the first stack, so Back returns. `MainWindow` tells the history about activations (`refresh_current`), selection changes and edits made in the editor, and ignores its own changes while it shows a place, because walking the list makes no entry; after showing a place it reports where the user ended up. Showing a place focuses its group, opens the document there again when it was closed (a file that is gone is forgotten and the walk goes on or stops), and selects the saved lines and columns, clamped to the text. The places of a group that is closed, and of an untitled document that no tab shows any more, are dropped; a document that is saved under a name, and a tab moved to another group, keep their places. Edits that extensions make are not places. The items are enabled by the context keys `canNavigateBack`, `canNavigateForward` and `canNavigateToLastEditLocation`, which the menu reads. VS Code binds Back to Ctrl+Alt+- on Linux, Alt+Left on Windows and Ctrl+- on macOS, Forward to Ctrl+Shift+- (Alt+Right on Windows), the mouse buttons for both, and Last Edit Location to Ctrl+K Ctrl+Q.

File > New Window (`workbench.action.newWindow`, Ctrl+Shift+N) starts another editor: `MainWindow::open_new_window` runs the program that is running (`QCoreApplication::applicationFilePath`, or `Options::executable`) with no arguments, with the environment of this process and in its working directory, or the temporary directory when that is gone, so a new window is an empty window with an extension host of its own. `platform::spawn_detached` starts it in a session of its own, so that nothing ends it when the window that started it closes, and a thread collects its exit status when it ends first; the window that asked is not affected. A program that cannot be started is reported in the status bar. `Options::start_process` replaces the start in tests, which check the process specification.

File > Open Recent > Reopen Closed Editor (`workbench.action.reopenClosedEditor`, Ctrl+Shift+T) opens the editor that was closed last, again. `workbench::ClosedEditors` keeps the editors closed in the session with the rules of VS Code's history service: at most 20, the oldest forgotten first, an editor that is closed again replaces its earlier entry, and the editors that one operation closed (Close Others, Close to the Right, Close Saved, Close Editor Group) come back together, in the order they were closed. An entry has the group, the position of the tab in it, the document, every selection as lines and columns, and, for an untitled document, its text, because that is gone with the editor. `MainWindow` records an editor when it closes it (`record_closed`), unless it is an untitled document with no text, and it starts a batch for each operation that closes editors (`ClosingScope`, nested operations share the batch). Reopening takes the newest batch and opens each of its editors in its group, or in the focused group when the group is gone (a group closes when its last tab does), at the position of its tab, makes the last of them the shown one, and selects what was selected, clamped to the text; a file is read again, so changes that were discarded with the editor are not back, and an untitled document comes back as a new untitled document that holds the text and has unsaved changes. An editor whose document is in its group already, and a file that no longer exists (which the status bar mentions), do not count, and when none of the batch could be opened the batch before it is tried. The list is not saved when the window closes. The item is enabled by the context key `canReopenClosedEditor`.

Go > Go to Line/Column... (`workbench.action.gotoLine`, Ctrl+G) opens the popup of quick access with `:` in its field, over the shown document, and moves the caret as the text after the colon is typed. `core::parse_go_to_line` reads it with VS Code's rules: a line number that is kept within the text (negative numbers count from the end, `-1` being the last line), optionally followed by `:`, `,` or `#` and a column that is kept within the line, where a negative number counts from the end, a tab counts up to the next tab stop of `editor.tabSize`, and a column inside a tab falls on the nearer edge of it. The one item of the list says what Enter does (`Press 'Enter' to go to line 12 at column 4.`, or what to type next), and is disabled while the text names no line, so that Enter then leaves the quick pick open; the list is not filtered by the text (`QuickPick::set_filtering`). Enter keeps the caret and adds a place to the navigation history as a navigation, so Back returns to where the caret was even when the line is near it; the places the caret passes while the text is typed are not added. Escape, the focus leaving the quick pick, or the popup turning into another use puts back every selection and the scroll position. Without a document the item says to open a text editor first. Ctrl+G pressed again leaves what was typed. Columns count each code point as one column, so wide characters and combining marks are not measured as VS Code measures them, and `::` (go to an offset) is not offered.

Go > Go to Bracket (`editor.action.jumpToBracket`, Ctrl+Shift+\\) moves each caret as `core::jump_to_bracket` says, with VS Code's rules: a caret before or after a bracket of a matched pair goes to the other bracket of the pair (between two brackets, the later one counts), a caret inside a pair goes to its closing bracket, and otherwise the caret goes to the next bracket of any kind, or stays. `core::bracket_pairs` matches `()`, `[]` and `{}` as VS Code's bracket pair parser does: a closing bracket closes the nearest open bracket of its kind and leaves the open brackets inside it unmatched, and a closing bracket with nothing to close is ignored. The text is not tokenized, so a bracket in a string or a comment counts.

Selection > Expand Selection and Shrink Selection (`editor.action.smartSelect.expand` and `.shrink`, Shift+Alt+Right and Left; Ctrl+Cmd+Shift or Ctrl+Shift with the arrows on macOS) step every selection through the ranges that `core::selection_ranges` lists around its active end, as VS Code's smart select does when no language provides ranges (ranges from the syntax of the language are not provided). The ranges that contain the selection, smallest first, are: the part of a word between camelCase, `_` and `-` boundaries, the word, a line of blanks, the inside and then the whole of each bracket pair around the caret, and the whole text. A multi-line pair also gives the text from the first non-blank character of the line that opens it, and the whole of that line, up to its closing bracket; a pair whose opening bracket starts its own line does the same for the line above when that line holds text. Where a range covers other lines than the one before it, the lines of that one come between them, without their leading and trailing blanks and then whole. `EditController` keeps each selection's ranges and position among them while the document version and the selections are those that the last step left, so Shrink Selection goes back through the same ranges; after any other change the ranges are computed again from the selections as they are, and Shrink Selection has nowhere to go. A step that would select the range the selection already is skips to the next. Selections that grow into each other are merged, and Shrink Selection separates them again.

`EditorLayout::apply_layout(orientation, shape)` arranges the groups as one of View > Editor Layout (`workbench.action.editorLayoutSingle` to `TwoColumnsBottom`) says, in the trees of `editorActions.ts`: a splitter of the orientation with the shape's children, each a group or a splitter of the other orientation, every splitter with equal shares (Grid 2x2 is two columns of two rows, Two Rows Right is a group beside two stacked ones, Two Columns Bottom a group over two side by side). The groups that exist fill the groups of the shape in the order they are shown; with fewer places the tabs of the extra groups are added at the end of the last group that stays, skipping documents it has, so no document is closed, and the group that had the focus passes it, with its tab in front, to that last group; with more places new groups are empty. `flip()` (`workbench.action.toggleEditorGroupLayout`, Shift+Alt+0 and Cmd+Alt+0 on macOS) turns every splitter the other way and keeps the order and the shares, and does nothing for one group. The layouts have no key. VS Code's Move and Copy Editor into a new window are not part of this.

The color themes that ship with the editor are VS Code's default themes, copied unchanged into `resources/themes` with a `themes.json` that lists them (`id`, `label`, `uiTheme`, file) and the VS Code license text; `THIRD_PARTY_NOTICES.md` names them. They are data the editor needs without the VS Code checkout, which is only a build-time dependency. `ui::themes_directory` finds them: `share/anvil/themes` next to the `bin` directory of an installed editor (CMake installs them there, with the license files in `share/doc/anvil`), and otherwise the source tree's `resources/themes`, for an editor run from its build directory. The `workbench.colorTheme` setting names a theme by its `id`; its default is `Dark 2026`, VS Code's default in the pinned release, and is one constant (`EditorDefaults::color_theme`). `scripts/sync-themes.mjs` refreshes the copies from the checkout, and a test fails when they differ.

`ui::ThemeStore` lists the shipped themes from `themes.json`, applies the one the `workbench.colorTheme` setting names (the window reads the setting at startup and whenever the settings file changes, with the default theme as the fallback at startup), and gives its colors to the workbench color lookup in one step, so every part repaints once. A name that is not a theme and a theme that cannot be loaded leave the applied theme as it is and are reported once in the status bar and in the log. A theme that leaves a key of the lookup's table unset gets what VS Code's color registry would give it as far as the editor has it: the value of the key the table says it defaults to (`editorGutter.background` follows `editor.background`, `sash.hoverBorder` follows `focusBorder`), and otherwise the value in the default theme of the same kind, Dark 2026 or Light 2026, high contrast themes included. A key that VS Code gives no default (`statusBar.border`, `editorGroupHeader.tabsBorder`, `tab.activeBorder`, `tab.hoverBackground`, `toolbar.hoverBackground`) is `optional` in the table: it stays unset unless the theme sets it, and the part that uses it draws the line or the highlight only when it is set; `toolbar.hoverBackground` has the registry's dark and light defaults instead. The editor view reads `editor.background`, `editor.foreground`, `editor.selectionBackground`, `editor.lineHighlightBackground`, `editorLineNumber.foreground`, `editorLineNumber.activeForeground`, `editorCursor.foreground`, `editorGutter.background`, `editor.findMatchBackground` and `editor.findMatchHighlightBackground`; the match the selection is on is the current one. Colors keep their alpha, and text under a selection keeps its color when the theme sets the selection's background. Syntax colors come with the highlighter, from `ThemeStore::color_theme()` and the token theme matcher. Themes that extensions contribute in `contributes.themes` (read by `exthost::read_contributions` with the path inside the extension's directory, the label from `package.nls.json` and `uiTheme` defaulting to `vs-dark`) are added after the shipped ones by `add_themes`, once the extension host has started and before the `workbench.colorTheme` setting is applied. A theme whose id is listed already is left out and logged, so a shipped theme wins over an extension's and the first extension over a later one; a theme whose file is missing is listed as unavailable and fails like any other that cannot be loaded when it is selected, without affecting the others.

File > Preferences > Themes > Color Theme (`workbench.action.selectTheme`, Ctrl+K Ctrl+T) opens the quick pick of color themes (`MainWindow::select_color_theme`). `ThemeStore::picker_groups` orders the themes as VS Code's picker does: dark themes, light themes, then high contrast themes, each under its heading, with the default theme (Dark 2026 or Light 2026) first and the rest by label, ignoring case; a theme is shown by its label, with its id after it when that differs, and one whose file is missing is shown disabled. The current theme is the chosen row. Each row the chosen row moves to (`QuickPick::active_changed`, which the arrow keys, the mouse and typing a filter all cause) is applied at once, so the colors of the window show the theme; Enter writes the theme's id to `workbench.colorTheme` with `MainWindow::change_setting`, which applies it through the settings like any other change of that setting, and Escape, or the focus leaving the quick pick, applies the theme that was current when it opened. The quick pick is the one that the command palette uses, through `MainWindow::pick_from`, whose hooks (`PickHooks`) say which item starts as the chosen row, hear of the chosen row moving, and hear of a close without a choice. A window with no themes says so in the status bar. File icon themes, product icon themes and themes from a gallery are not offered.

`core::score_item` ranks labels against a query as VS Code's quick pick does: a port of the behavior of `fuzzyScorer.ts`. A query is prepared once (`prepare_query`: quotes, `*`, `…`, whitespace and a trailing `#` removed, words split on spaces) and then scores any number of items, each a label with an optional description and file path. A score of zero is no match; a match in the label scores above one that needed the description, a prefix of the label above any other match in it, and a query equal to the item's path highest. Matched characters are reported as ranges for highlighting, and `compare_items` orders two scored items by score, then by how compact the match is, then by label length. Text is UTF-8 and the algorithm and all reported positions use UTF-16 code units, as VS Code's do. Case is folded for ASCII letters only, and the last tie-break compares code units instead of using a locale collator; the module documents both. `tests/core/data/fuzzy_cases.json` holds results recorded from VS Code's own scorer (`scripts/generate-fuzzy-cases.mjs`), which the tests replay.

## Commands

The editor's operations are commands in `ui::CommandRegistry`, keyed by VS Code's command ids (`undo`, `cursorLeft`, `editor.action.clipboardCopyAction`, `workbench.action.files.save`) and each with a palette title. Menus run a command by its id, and `MainWindow` hands every registered command to the extension host's `CommandsService` when the host starts, so `vscode.commands.executeCommand` runs the same code as the menu. A command receives the JSON array of arguments and ignores what it does not use. [Adding an editor command](howto/adding-a-command.md) describes how to register one.

`ui::KeybindingService` runs commands from the keyboard. It is an event filter on the application, so it sees a key press before the widget that has the focus does, and `key_step_from_event` turns the press into a `core::KeyStep`: the key is the one at that place on a US keyboard, found from the scan code on Linux so that a binding such as `ctrl+k` works on any layout, and from Qt's key otherwise (digits, punctuation with and without Shift, the keypad by `Qt::KeypadModifier`, Shift+Tab as Tab with Shift), and on macOS the Control and Command modifiers swap names so that `cmd` is the Command key. The dispatcher decides what the step does. A bound press runs its command through the command registry (or the extension host for a command the registry does not have) and does not reach the widget; any other press goes on unchanged, so typing is untouched. A chord in progress shows "(Ctrl+K) was pressed. Waiting for second key of chord..." in the status bar until it ends, without replacing another message that has appeared since. A press is left alone while a modal dialog is open, which runs a nested event loop in which a shortcut must not reach the window behind it, and while an input method composes text in the editor. A `ShortcutOverride` event for a key that is bound or starts a chord is accepted, so that a Qt shortcut or a menu mnemonic does not take the key first. The context keys that `when` clauses read are filled from the focus at the time of the press: `editorFocus`, `editorTextFocus`, `inputFocus`, `textInputFocus`, `editorHasSelection`, `editorHasMultipleSelections`, `activeEditorGroupEmpty`, `multipleEditorGroups`, `resourceScheme`, `resourceFilename`, `resourceExtname`, `resourceLangId`, `isLinux`, `isWindows` and `isMac`, plus the keys that extensions set with the `setContext` command. The built-in bindings are one table in `src/ui/default_keybindings.cpp` with the keys of VS Code on Linux, Windows and macOS for every command the editor has; the editor's own commands apply under `editorTextFocus`, so a text field such as the find field keeps Ctrl+Z, the arrow keys and the clipboard keys for itself. Menus show the primary binding of their command as it is when the menu opens, so a change of the bindings shows without rebuilding the menus.

The command palette (`workbench.action.showCommands`, Ctrl+Shift+P and F1) lists the registry's commands by title and the commands that extensions contribute by `Category: Title`, ranks them with the fuzzy matcher and highlights the matched characters, and puts the recently used ones first. It is a `ui::QuickPick`: a popup over the top center of the window with a filter field and a list that filters and ranks its own items, reports the chosen item by position, and gives the focus back to where it was. The same widget serves the extension API's quick pick. Its look is VS Code's: a card with rounded corners (`corner_radius`) and a border, over a shadow that is a widget of its own behind it because a child cannot draw outside its bounds (`widget.shadow`), the filter field with its own border (`input.border`, `focusBorder` while it has the focus) inside a padded header, rows of 22 px whose highlight is inset and rounded, and at most 20 rows (fewer in a window that is not high enough). A `QuickPickItem` with `separator` set is a divider: with no filter typed it draws a line (`pickerGroup.border`) above the next row, which is not the first, and its label at that row's right end in the description color; it is never a row, so it is never chosen or stopped on, and while a filter is typed it is left out and not matched, because the matches of all the groups are ranked together. The positions that `accepted` reports are those of the list that was set, separators included. A command chosen in the palette runs through the extension host's command service when a host is running, so extension commands and the editor's own take one path, and it does not run while a dialog is open. What the extensions contribute comes from `exthost::read_contributions`, which reads `contributes.commands`, `contributes.keybindings` and `contributes.menus.commandPalette` from each extension's `package.json` as plain data when the host starts, with `%key%` placeholders filled from `package.nls.json` and a title or category written as `{value, original}` read as its value. A section that is not what VS Code documents, and an entry that cannot be used, is logged once with the extension's id and skipped, so the other sections and extensions load. Only commands that an extension contributes with a title are in the palette; one it registers without contributing is not, as in VS Code. A command is hidden while its `commandPalette` rules exist and none of their `when` expressions holds in the context keys at the moment the palette opens; one whose `enablement` is false is shown dimmed (`QuickPickItem::disabled`), cannot be chosen, and does not run from a key binding or the status bar either. An expression that cannot be read counts as true, so a typo in a manifest does not take a command away. The keys of `contributes.keybindings` become key bindings with the source `extension`, choosing `mac`, `linux` or `win` over `key` for the platform; the table ranks them below the user's and above the editor's own. A contributed command that no extension has registered yet is run by activating the extensions that name `onCommand:<id>` and looking again, and the init data names that event for every contributed command, as VS Code does, so an extension that lists no activation events starts when its first command is used.

Go to File (`workbench.action.quickOpen`, Ctrl+P and Ctrl+E, Cmd+P on macOS) the command palette and Go to Line/Column are one popup, as quick access is in VS Code, and the first character of its text says what it does: `>` the command palette, `:` Go to Line/Column, anything else a search for files. Each command opens it with its character, and typing or removing one turns it into the other use, keeping the text and the cursor (`MainWindow::follow_quick_access_text`). The other lists that use the popup, such as the language and theme pickers, stay what they are whatever is typed, and one that is replaced is dismissed, which undoes a preview. `ui::QuickOpen` takes the popup over for the files, with its filtering off, and gives it up with `end`. With an empty filter it offers the files that the window has shown, the most recently first, closed ones included and ones that are gone left out. With a filter those that match come first, best first, and then the files of the workspace folder that match, 512 at most in all; a query is matched with `core::score_item` against the name as the label and the folder as the description, ordered by `core::compare_items`, and the matched characters are highlighted. The folder is listed with ripgrep each time the popup opens ([File search](#file-search)), and one thread both reads the listing and matches, keeping only the best 512, so that a key press costs the UI thread nothing that grows with the number of files. Results carry the number of the filter they answer, and those of an older one are dropped. While the listing runs the popup shows what matches so far, every tenth of a second at most, and a row that the user moved to stays chosen. Enter pressed before the shown items answer the filter is held until they do, so that it does not choose from the results of what was typed before. Closing the popup or choosing ends the listing. The command run again while the popup is open chooses the next row, as Ctrl+P does in VS Code. Without a folder, or where no ripgrep is found, which the status bar says, the open documents are offered instead; a listing that fails is reported in the status bar and what it listed is kept. The chosen file opens in the focused group.

## Window structure

The menu bar is VS Code's: File, Edit, Selection, View, Go, Run, Terminal and Help, with their submenus, items, separators and mnemonics ([#130](https://github.com/djangbahevans/project-anvil/issues/130)). `scripts/generate-menus.mjs` produces `workbench::menu_table` from the pinned VS Code: it loads the compiled desktop workbench in Node with a minimal browser, creates every workbench contribution and the views service against inert services, reads the menus back from `MenuRegistry`, and writes them in VS Code's order (group, then `order`, then title) with a separator between groups. Menus of Linux and Windows are the same; the table is the one of Linux and Windows, and a macOS table, whose app menu holds About, Preferences and Quit, is not generated yet ([#135](https://github.com/djangbahevans/project-anvil/issues/135)). `workbench::top_level_menus` and `workbench::menu_items` turn the table into the entries that a context shows: an entry whose `when` clause does not hold is left out, so is a submenu with nothing left in it, and a separator stays only between two entries. The window also leaves out the entries that Anvil does not provide: `workbench::menu_items` takes a list of ids to leave out, which acts like a `when` clause that does not hold (a submenu that is left out takes its entries with it, and the separators around the gap close up), and `workbench::unprovided_menu_items` is that list, one place for them, with the reason by each: the Help items that need webviews (Welcome, Editor Playground, Open Walkthrough, Show Release Notes, Get Started with Accessibility Features), the chat (Ask @vscode), the pages of Microsoft's product (Video Tutorials, Tips and Tricks, Join Us on YouTube, Search Feature Requests, Privacy Statement) and the tools of Chromium and Electron (Toggle Developer Tools, Open Process Explorer). The table stays as VS Code has it, and offering an item later is removing its id from the list, so that the Help menu lists Show All Commands, Documentation, Keyboard Shortcuts Reference, Report Issue, View License and About. Documentation, Report Issue and View License (`workbench.action.openDocumentationUrl`, `workbench.action.openIssueReporter` and `workbench.action.openLicenseUrl`, which VS Code binds to no key) open the project's README, its new issue page and its license, whose addresses are in `ui/project_links.hpp`, in the system's browser through `QDesktopServices` (`MainWindow::open_project_page`); `MainWindowOptions::open_url` replaces that for the tests, and when the browser cannot be started the status bar gives the address. About (`workbench.action.showAboutDialog`, no key) opens a `QMessageBox` that is shown with `open()`, so that it is modal to the window without a nested event loop in which the extension host would run commands; a second run raises the open one. `ui::about_text` builds its text from `ui::AboutVersions`, in which a version that is unknown reads "not available": the version of Anvil is the `VERSION` of the `project()` call, which reaches `anvil_ui` as the compile definition `ANVIL_VERSION` (`ui::anvil_version`); Qt is `qVersion()` and, when the library in use differs from the one the build saw, `QT_VERSION_STR`; the extension host is VS Code's own, so its version is the `version` of `package.json` in the VS Code directory that the window is configured with (`ui::read_vscode_version`, read when the window starts, and not available without an extension host). Keyboard Shortcuts Reference (`workbench.action.keybindingsReference`, Ctrl+K Ctrl+R as in VS Code, which opens a PDF of Microsoft's) opens a new untitled document with the live key table: `ui::keybindings_reference` takes the command titles of the `CommandRegistry` and the `KeybindingService`'s table, which is the defaults with the extensions' and the user's bindings applied, and writes a heading, a blank line and a line `<title><TAB><keys>` for every command that has a key, sorted by title without regard to case and then by id, with the keys spelled for the platform and separated by `, `. A command without a title is listed by its id, and one whose bindings the user's file removes is not listed. The document is created with that text, so it is not modified until the user edits it, and each run makes another one. The other items are disabled until their commands exist. The table also holds each item's `precondition` and `toggled` clauses: an item whose `precondition` does not hold is disabled, and an item with a `toggled` clause is checkable and checked while it holds (Auto Save, Minimap, Word Wrap, the side bar). The clauses read settings as `config.<key>`; the generator reads the default of each such setting from VS Code's configuration registry into `menu_config_defaults`, and `workbench::set_menu_config_context` sets `config.<key>` to the default and then to every value of the settings file, spelled flat or nested, with a flat key winning as it does in `core::Settings`. Lists, strings, numbers and booleans become context values; objects are flattened to their leaves. `workbench::set_menu_context_defaults` sets the keys that the clauses read and the editor has no state for: the capabilities of a desktop window (`openFolderWorkspaceSupport`, `terminalProcessSupported`) and the views that are listed whether or not they have content are true, and `workbenchState` is `empty`, so "Close Folder" waits for a folder and "Open Folder..." shows. `MainWindow` fills a menu when it opens, from the settings and the window state at that moment, so a changed setting changes the check mark the next time the menu opens (`MainWindow::fill_context` supplies `activeEditor`, `editorIsOpen`, `dirtyWorkingCopies`, `isFullscreen`, `sideBarVisible` and `panelVisible`, which the clauses of the items that already work read): an item runs the command with its id from `ui::CommandRegistry` and shows its primary key binding; an item with no such command is disabled with the tooltip "<title> is not available yet" and is enabled the next time the menu opens after the command is registered. `ui::MenuStyle` lays an item out as VS Code does: 24 px high, the label 30 px from the left edge, the `check` codicon centered in the 32 px column before it, the shortcut right-aligned 30 px from the right edge whatever the other items hold, and the `chevron-right` codicon centered 21 px from the right edge of a submenu item; a separator is 9 px high with its 1 px line in the middle. A menu has no style sheet of its own, because `QStyleSheetStyle` would draw its items instead of the style. The mnemonic of Run (Alt+R) is dropped, because Alt+C, Alt+W and Alt+R are the find bar's option shortcuts and a menu that shares one makes Qt trigger neither.

The window is arranged from fixed parts, in VS Code's positions and with its part ids: the title bar above; the activity bar at the left edge; the primary sidebar; the editor area; the bottom panel; and the status bar below ([0014](adr/0014-workbench-layout.md)). Splitters resize the sidebar and the panel, and each part can be hidden. On Linux and Windows the window has no frame of its own and draws the title bar (below); on macOS it has the system's frame and the global menu bar.

`ui::Workbench` is the window's central widget and arranges the parts: the activity bar at the left edge (48 px), a horizontal splitter with the sidebar and, beside it, a vertical splitter with the editor area above the panel, while the status bar, which the window hands over, runs along the bottom edge. Each part has a `Part` and VS Code's id (`workbench.parts.sidebar`), is shown and hidden with `set_visible` or `toggle`, and reports a size. The sidebar and the panel start hidden, and the activity bar shows while a container is registered for the sidebar, which the explorer always is; showing one gives it the size it had when it was hidden (300 px the first time), within its minimum (170 px wide, 77 px high) and what the editor area keeps (220 by 70 px), and hiding one returns its space to the editor area. The splitter handles are 4 px sashes that show the border color of the part as a 1 px line and the `sash.hoverBorder` color while hovered or dragged. The activity bar and the sidebar are filled from `ui::ViewContainerRegistry`: a view container has an id, a title, a monochrome icon, a location (sidebar or panel), an order and a function that makes its widget, and the registry knows nothing about what is inside. `ui::Sidebar` shows a button for each sidebar container in the activity bar (hidden while there are none) with the active one marked on its left edge, and the chosen container in the sidebar under its title in capitals. Choosing a container shows the sidebar with it, choosing the one that is shown hides the sidebar, and showing the sidebar another way shows the last active container, or the first. A container's widget is made the first time it is shown and kept, and removed with the container. Icons are drawn as masks in the foreground or the inactive color of the activity bar.

`ui::Panel` fills the bottom panel the same way: a 35 px header with a tab for each container registered for the panel (titles in capitals, the active one underlined), a button that maximizes the panel and one that closes it, and the chosen container below. Choosing a tab shows that container, closing hides the panel and keeps the container, and showing the panel another way shows the last active container or the first. Maximizing hides the editor area so that the panel fills it, and restoring shows the editor area again with the panel at the size it had; hiding a maximized panel restores it. The widgets of the sidebar and the panel come from `ui::ViewContainerStack`, which makes a container's widget the first time it is shown and deletes it with the container. `workbench.action.toggleMaximizedPanel` toggles the maximized state.

A window opens as the last one was left. `workbench::StateStore` (no Qt) keeps what follows from using the editor in `state` below the user's configuration directory, apart from the settings and the storage of extensions ([0019](adr/0019-editor-state-store.md)): `global.json`, `workspaces/<workspace id>.json` for a folder and `no-folder.json` without one, each a JSON object. A write reads the file again and changes only the keys whose value changed, so two windows keep what the other wrote to other keys; a file that is not a JSON object is read as empty and logged. `ui::WindowStateKeeper` applies the state before the window is first shown, writes it half a second after the last change and when the window closes, and ignores a value of the wrong type or out of range.

| File | Key | Value |
| --- | --- | --- |
| global | `window.x`, `window.y`, `window.width`, `window.height` | the place of the window when it is neither maximized nor in full screen |
| global | `window.maximized` | `true` or `false` |
| global | `layout.sidebar.width` | the width of the sidebar in pixels |
| global | `layout.panel.size.top`, `.bottom`, `.left`, `.right` | the size of the panel at that position: a height at the top and the bottom, a width at the sides |
| workspace | `layout.sidebar.visible`, `layout.panel.visible` | `true` or `false` |
| workspace | `layout.panel.position` | `top`, `bottom`, `left` or `right` |
| workspace | `layout.panel.maximized` | `true` or `false` |
| workspace | `layout.sidebar.activeContainer`, `layout.panel.activeContainer` | the id of a view container |
| workspace | `explorer.expandedFolders` | the folders that are expanded in the explorer, as paths relative to the workspace folder with forward slashes |

A saved size below the minimum of its part is raised to it, and sizes are restored as saved at any zoom level. A window that has less room than the saved sizes need shows the parts smaller, and those sizes are then saved. A saved window whose top no screen shows is centered on a screen and limited to its size; full screen is not restored, and a window system that places windows itself, such as Wayland, ignores the position. A restored container's view is made only when its part shows. What a setting governs, such as the side of the sidebar, is not state, and a window closed in Zen Mode saves the parts as they were outside it. Opening or closing a folder saves to the file of the workspace that is left and keeps the layout on screen, which later saves record for the new workspace.

The explorer opens a folder with the folders that were expanded in it, including those below a collapsed folder, as VS Code does. Directories are read on worker threads, so they are expanded one level at a time as their rows arrive, and one below a collapsed folder is listed only when the user expands that folder. A saved folder is dropped when the folder above it has been read and the disk no longer has it; one that has not been reached stays saved, and so does the whole list while the explorer is never shown.

The explorer is the first sidebar container (`workbench.view.explorer`, title Explorer, the Codicons `files` icon, order 0), registered by `MainWindow` and made when it is first shown. `ui::ExplorerView` shows the name of the workspace folder in capitals above a `QTreeView` over `ui::ExplorerModel`, which adapts `core::FileTree` (see Files) and lists with `platform::list_directory`; Qt's `QFileSystemModel` is not used, so that a file system that is not the local one can plug in later. A directory is read when the tree first expands it (`canFetchMore` and `fetchMore`), and the folder itself when it is set, on a worker thread: the model asks a `ListingRunner` (`thread_listing_runner`, a thread for each listing that gives its result back through the event loop; tests use `immediate_listing_runner` or a runner that they drive) to run a `core::DirectoryReader` of the tree, which lists, filters and sorts, and until the result arrives the directory has one row, "Loading…" (`PlaceholderRole`, drawn in the description color and italic, not selectable, never activated). When the result arrives the row goes, the listing is adopted into the tree (`FileTree::adopt`), and the entries are inserted `ExplorerModel::batch_size` (500) at a time, each batch in an event of its own, so that no step blocks the event loop for long: a directory of 50,000 files blocks it for 10–20 ms at most in the Debug preset, where inserting all of them in one step takes longer than the test allows for the whole expansion. A result that a runner gives before `run` returns is not used until the event loop runs, because the view calls `fetchMore` in the middle of laying out an expansion and cannot have the rows of the directory replaced from inside that call. Collapsing a directory that is loading (`ExplorerModel::cancel_loading`, from the view's `collapsed` signal), closing the folder or opening another one, and the removal of the row of a directory that is loading all stop its listing with a `std::stop_token`, which the reader looks at after the listing and before the sort (the listing is one call of the lister and is not interrupted), remove the rows that it had, and drop the result that arrives later; expanding the directory again reads it again. A collapsed directory that has been read keeps its entries. Events that name a directory while it loads, and new `files.exclude` patterns, are applied when it has loaded, by reading it again once. The tree draws what the theme gives: rows of 22 px with the twisties of the Codicons (`chevron-right`, `chevron-down`) in the first 16 px, an indent of 8 px per level, and the colors `list.activeSelectionBackground` and `list.activeSelectionForeground` while the tree has the keyboard focus, `list.inactiveSelectionBackground` and `list.inactiveSelectionForeground` while it does not, `list.hoverBackground` and `list.hoverForeground` under the mouse, and `sideBar.background` and `sideBar.foreground` otherwise. Enter and a double click open a file with `MainWindow::open_file` and expand or collapse a folder; a single click only selects. The arrow keys, Home, End, Page Up, Page Down, the right arrow (expand, then move to the first child) and the left arrow (collapse, then move to the parent) are those of `QTreeView`. A directory that cannot be read shows no children and keeps the message of the failure as its tooltip. `files.exclude` is read from the settings as VS Code reads it: the user's object is laid over the default one (`core::FileExcludes::from_settings`), so a default pattern stays unless the setting turns it off with `false`. A change of the setting applies to the open tree by reading the open directories again and changing only the rows that appear or disappear (`ExplorerModel::set_excludes`), so what is expanded and selected stays. A value of `files.exclude` that is an object (a `when` condition) is logged and ignored. With no folder open the view shows "You have not yet opened a folder." and an Open Folder button that runs `workbench.action.files.openFolder`, and opening or closing a folder shows or clears the tree. The tree follows the disk. `ExplorerModel` starts a non-recursive `platform::FileWatcher` on the folder when it is set and adds each directory it reads (`add_directory`, before the listing, so that a change in between is not missed), so it watches only the directories that are open, whatever the size of the project: a recursive watch of a folder with ten thousand directories takes seconds to start, and one watcher with one thread serves every open directory where a watcher per directory would use up the inotify instances that the system allows to a user. A timer on the UI thread (100 ms) takes the events (`process_file_events`), collects the directories that they name, and reads each of those that has rows again once with `FileTree::refresh`, however many events name it. Rows that went away or changed are removed and new ones inserted in runs, so a burst is a few model signals, and what is expanded stays; the watches of removed rows are dropped with them. A folder that is deleted disappears with what was open under it, a folder that is renamed from outside shows under its new name, collapsed, and a selected row that disappears moves the selection to the row that takes its place, or to the parent when none is left. A directory that was never read is not watched and not listed. A watch that cannot start, a directory that cannot be added (`limit_exceeded`), and lost events (the system's queue overflowed) are said once in the status bar; after lost events every open directory is read again. A platform that cannot watch (`unsupported`) says nothing and the tree stays as it was read. `ExplorerModel` talks to the watcher through `DirectoryWatch`, so tests replace it with a fake that they drive. Reading a directory again after an event is synchronous on the UI thread: a burst that adds ten thousand files to an open directory blocks the event loop for a fraction of a second (measured in Debug: about 0.2 s). Only the first reading of a directory is done on a worker. The view makes, renames and deletes files and folders (`new_file`, `new_folder`, `rename_selected`, `trash_selected`, `delete_selected`; the window's commands and keys are in the next paragraph). A new item is a row at the top of the folder that is `ExplorerModel`'s but is not an entry of the disk: `add_pending_entry` inserts it (`PendingRole`, an empty name, editable) in a directory that has been read (`is_read`), `synchronize` leaves it where it is when the directory is read again, and `remove_pending_entry`, the closing of the folder or the removal of its parent drops it. A folder that was not read is expanded first and the row comes when `directory_read` says that its entries are in. The field is the delegate's editor, made by the view (`NameEditor`, a `QLineEdit` and under it the reason why the name is refused, a label of the viewport that follows the field); the delegate's own event filter is off, because it would commit on Enter and on losing the focus and close the field on Escape before the view looks at the name. Enter validates the name (empty, a leading slash, a separator, `.` and `..`, an existing name) and keeps the field open with the reason under it when it is refused, otherwise it makes the file (`platform::write_file` of nothing), the folder (`platform::make_directory`) or renames (`platform::rename_path` without overwriting), closes the field and reads the directory at once with `ExplorerModel::reload` instead of waiting for the watch. The field also checks the name as the text changes. Leaving the field accepts a valid name and drops an invalid or empty one. A failure of the system closes the field and is reported through `operation_failed`. A delete takes the paths of the selected rows before it asks, because the question (`ExplorerActions::confirm`, a modal dialog) runs a nested event loop in which the selection can change, asks unless `set_confirm_delete(false)`, and moves each path to the trash (`ExplorerActions::move_to_trash`, `QFile::moveToTrash`) or removes it with `platform::remove_path`; the trash and the question are replaced in tests. The signals `created`, `renamed` and `deleted` tell the window what happened.

`MainWindow` registers the commands `explorer.newFile`, `explorer.newFolder`, `renameFile`, `moveFileToTrash`, `deleteFile` and `revealFileInOS`, with VS Code's ids and keys (`default_keybindings.cpp`), which apply when the context keys `filesExplorerFocus` (the focus is in the explorer), `explorerViewletVisible` and `!inputFocus` hold, so that Delete in the field edits its text. `explorerResourceIsRoot` is true when nothing is selected and `explorerResourceMoveableToTrash` when a row is selected and `files.enableTrash` is on. The context menu is built by `MainWindow::build_explorer_menu` from the commands that fit the selected row. The documents follow what the explorer does (`explorer_renamed`, `explorer_deleted`), the way they follow an extension's workspace edit: the window tells the extension host (`DocumentsService::files_renamed` and `files_deleted`), whose observer callbacks re-key or close the tabs through `document_renamed` and `document_deleted`, and handles itself the documents that the host does not have or has not started; a rename keeps the tab, the undo history and the unsaved changes, a delete closes the tab of a document without unsaved changes and keeps the others, and a new file opens in an editor. `revealFileInOS` opens the folder that holds the item with `QDesktopServices::openUrl`, which on every platform shows the folder and does not select the item. The view has no file icons.

The tree selects several rows (`ExtendedSelection`). A command on one item (rename, new file, reveal) takes `focused_row`, the current row when it is selected; a delete and a drag take every selected path, without those that lie below another selected one (`paths_of`), so a folder and a file in it are handled once. The tree drags the rows itself, from the press to the release, and does not use `QDrag`, which runs an event loop of its own: a press on a label keeps the rows to drag (the selection when the pressed row is selected, else that row), a movement of `QApplication::startDragDistance` starts the drag, and the moves that follow are not given to `QTreeView`, which would extend the selection with them. The view says which folder takes a drop (`folder_to_drop_into`: the folder under the pointer, the folder of a file under it, or the folder of the workspace below the rows; nothing for a folder dropped onto itself or below, or for items that are all there already), the tree highlights that folder and what shows below it with `list.dropBackground`, sets the cursor of a move, a copy or a refusal, and opens a closed folder that the pointer rests on for half a second. Escape, or a new press, ends a drag. Whether the drop moves or copies is read from the modifiers of the release. `drop_items` moves with `platform::rename_path` or copies with `platform::copy_path`. A move asks before anything changes (`ExplorerActions::confirm_move`), naming the items that would move: those that are not in the folder already and whose move is not refused. It does not ask for a copy, nor with `explorer.confirmDragAndDrop` off; checking "Do not ask me again" and moving makes the view report `move_confirmation_turned_off`, and the window writes the setting. A destination that exists then asks (`ExplorerActions::confirm`), acting on the paths that were dragged, whatever the selection has become; a folder that holds the item is never replaced by it, because replacing removes the target first; and a move does not replace a file with unsaved changes, which the window answers (`set_unsaved_changes_check`) before the question and again after it, since the question runs a nested event loop. A replaced destination is reported with `deleted` before the moved item is reported with `renamed`, so that the documents of the replaced file close before those of the moved one take its URI. A copy reports nothing but a replacement, and open documents stay where they are. The tree does not scroll by itself while a drag is at its edge. Typing letters is the keyboard search of `QTreeView`, which looks through the rows that show, so it reads no directory and passes over the "Loading…" row, which is not enabled.

The parts move. `Workbench::set_sidebar_side` puts the sidebar and the activity bar at the left or the right edge of the window, the activity bar at the outer side, and the indicator of the active button of the activity bar follows to the outer edge, as does the icon of the side bar button of the title bar. `Workbench::set_panel_position` puts the panel below the editor area, above it, or at its left or right; the splitter between them changes its orientation and the order of its children, and a panel at the left or the right has a minimum width of 300 px and no minimum height. Each position has its own size, a height at the top and the bottom and a width at the left and the right, so that moving the panel to a position it was at before gives it the size it had there; a position that was never used starts at 300 px. A hidden panel stays hidden when it moves, and a maximized panel stays maximized and takes the whole editor area at every position. Moving a part keeps the keyboard focus where it was. Three settings place the other parts and are applied at startup and on every change of the settings: `workbench.sideBar.location` (`left` or `right`), `workbench.statusBar.visible`, and `workbench.activityBar.location` (`default` shows the activity bar beside the sidebar, `hidden` hides it; `top` and `bottom` are valid values that show it as `default`, because it has no other place yet). The commands of View > Appearance write these settings with `MainWindow::change_setting`, so that they are kept in the settings file: `workbench.action.toggleStatusbarVisibility`, `workbench.action.toggleSidebarPosition` (the menu item names the side the sidebar moves to, from `config.workbench.sideBar.location`), `workbench.action.activityBarLocation.default`, `workbench.action.activityBarLocation.hide` and `workbench.action.toggleActivityBarVisibility`, which switches between the two. The panel position has no setting in VS Code; it is state of the workspace (see above) and the `panelPosition` context key that the Panel Position items check: `workbench.action.positionPanelTop`, `positionPanelLeft`, `positionPanelRight` and `positionPanelBottom`. VS Code binds none of these commands to a key.

View > Appearance > Zen Mode (`workbench.action.toggleZenMode`, Ctrl+K Z) and Centered Layout (`workbench.action.toggleCenteredLayout`) follow VS Code. `EditorArea::set_centered` gives a single group a margin of 19.09% of the width of the area at each side, painted in `editor.background`; with several groups the margins are gone and come back when one group is left, and the mode stays on in between. The margins cannot be dragged, and the width is always a proportion of the area. Zen Mode hides the sidebar and the panel, and with the settings `zenMode.hideActivityBar` and `zenMode.hideStatusBar` (both `true`) the activity bar and the status bar, centers the layout with `zenMode.centerLayout` (`true`) and puts the window into full screen with `zenMode.fullScreen` (`true`). The tab strips stay as `zenMode.showTabs` says (`multiple` by default, as in VS Code), see the tab bar modes below. Line numbers are not hidden because the editor has none yet. `MainWindow` remembers what Zen Mode changed: whether the sidebar and the panel were shown, whether the layout was already centered and whether the window was already in full screen, and ending Zen Mode gives back exactly that, so a part that was hidden before stays hidden, and a centered layout or a full screen window that was on before stays on. The status bar and the activity bar are shown from the settings and from Zen Mode together (`MainWindow::apply_part_visibility`), so that a change of a setting while Zen Mode is on does not show what it hides, and ends with the state the settings give. Leaving full screen while Zen Mode has entered it ends Zen Mode. The keyboard focus stays where it was when that part is still shown, and goes to the editor when it is not. Pressing Escape twice (`workbench.action.exitZenMode`) ends Zen Mode when the editor has the focus and has one selection at most: with several cursors the first Escape drops them, as in VS Code, where Escape has other uses before it starts the two-key binding. The context keys `inZenMode` and `isCenteredLayout` are what the menu items check.

View > Appearance > Tab Bar (Multiple Tabs, Single Tab, Hidden) sets `workbench.editor.showTabs`, through `workbench.action.showMultipleEditorTabs`, `workbench.action.showEditorTab` and `workbench.action.hideEditorTabs`, which write the setting with `MainWindow::change_setting` so that it is kept in the settings file, and the items check the mode that is on from `config.workbench.editor.showTabs`. `multiple` shows a tab for each editor of a group. `single` shows only the selected tab, as one tab as wide as the strip (`TabStrip::set_single`): the other tabs stay in the strip, with no area, so the mouse cannot reach them, they cannot be reordered, the strip never scrolls and assistive technology sees one tab; the selection, closing with the button or the middle click, and the tooltip work as for any tab, and a tab dropped from another strip goes before the shown tab or after the last one. `none` hides the strip, and the group keeps its editor, find bar and tabs: the editor takes the height of the strip, and where the strip was is part of the editor for dropping a tab. While Zen Mode is on the mode is `zenMode.showTabs`, and the Tab Bar submenu of the menu has the same three items for it (`workbench.action.zenShowMultipleEditorTabs`, `workbench.action.zenShowEditorTab` and `workbench.action.zenHideEditorTabs`), which write `zenMode.showTabs`; the commands of the first menu write `workbench.editor.showTabs` also during Zen Mode, and the mode they set shows when Zen Mode ends. `EditorArea::set_tabs_mode` sets the mode of every group and of the groups that come later. VS Code binds none of these commands to a key. The legacy boolean spelling of `workbench.editor.showTabs` is not read: a value that is not one of the three strings is reported by key name.

View > Toggle Sidebar (Ctrl+B) and Toggle Panel (Ctrl+J) run the commands `workbench.action.toggleSidebarVisibility` and `workbench.action.togglePanel`. View > Split Editor Right (Ctrl+\\), Split Editor Down, Focus Next Group, Focus Previous Group and Close Editor Group run `workbench.action.splitEditor`, `workbench.action.splitEditorDown`, `workbench.action.focusNextGroup`, `workbench.action.focusPreviousGroup` and `workbench.action.closeGroup`.

The sidebar and the panel host view containers: each is registered with an id, a title, an icon and a factory, and its widget is created the first time it is shown. The explorer, search, the terminal and extension tree views plug in the same way. The editor area is a tree of editor groups and splitters; the model of groups, their tabs and the split orientations is plain data with no widget types. Every part reads its colors by workbench color key through one lookup, `ui::WorkbenchColors`, that a color theme fills: a part asks for `statusBar.background` or `tab.activeBackground` and never holds a color. The keys that exist are one table in `src/ui/workbench_colors.cpp`, ordered by key, each with VS Code's name, a description of where it is used, and its fallback: what the theme gives another key (`sash.hoverBorder` follows `focusBorder`, as in VS Code) or a role of the palette, so the window looks as it does today when no theme is loaded. A theme replaces all its values at once and every part repaints once; asking for a key that is not in the table is a programming error and answers magenta. The parts, the quick pick, the command palette and the editor view read their colors this way. To give a part a color, add the key to the table, with a fallback, and read it through the lookup.

`ui::StatusBar` is a 22 px strip along the bottom edge that paints its items itself, in the UI font at 12 px, on `statusBar.background` with a 1 px `statusBar.border` line on top when the theme sets one. Items live in a left and a right group; an item has an id, a text, a tooltip, a foreground and a background (a workbench color key or a fixed color, resolved when painting), an optional command id and a priority, and a higher priority puts the item further to the left on either side, with items of equal priority in the order they were added. Items are set by id, so setting one adds it or replaces it, and setting an item to what it already is does nothing: the position item is set on every caret move and must not repaint or lay out again unless something changed. An item is its text plus 5 px of padding on each side, with 3 px between the padding of neighbors and at the edges, and a highlight on hover (`statusBarItem.hoverBackground`) and while pressed (`statusBarItem.activeBackground`) that covers the padding. Only an item with a command reacts to the mouse; a click emits `command_requested`, which the window runs like any command without adding it to the recently used commands of the palette. `show_message` replaces the left group with a text, for a time or until it is cleared; the right group stays. The window's own items are the cursor position (right, priority 100) and the state of the extension host (right, priority 0). Assistive technology sees the items through `AccessibleItems` (see `painted_accessibility.hpp`): the bar is a status bar whose children are its shown items in display order, left group then right group and without those a message hides, each static text or, with a command, a button, named by its text and described by its tooltip, with a press action that asks for the command like a click. A change of an item's text or tooltip signals a name or description change for that child, and setting an item to what it is signals nothing.

A widget that paints its items itself exposes them to assistive technology by implementing `AccessibleItems` (the items it shows, each with a key that survives the others changing, a name, a description, a role, a state, a rectangle and its actions, and what an action does) and calling `install_painted_accessibility()`. A generic accessible interface turns that into children that are created on demand, are dropped when their item is gone, and report their rectangle in screen coordinates. Notifications go through `notify_accessible_item`, which costs nothing while no assistive technology runs; `set_accessible_event_observer` lets a test see them, because the platform the tests run on never reports accessibility as active.

On Linux and Windows the window has no frame and its top row is `ui::TitleBar`, the part `workbench.parts.titlebar`, 35 px high ([0015](adr/0015-custom-title-bar.md)): the application icon, the window's `QMenuBar`, an empty area that shows the window title, and the minimize, maximize or restore, and close buttons, drawn with the Codicons font. The bar paints `titleBar.activeBackground` and `titleBar.activeForeground`, or the inactive pair while the window is not active, and a `titleBar.border` line below it when the theme sets one; the menu bar takes the bar's background and text, and its popups the `menu.*` colors (drawn by `ui::MenuStyle`, a `QProxyStyle` that every menu and submenu uses and that reads the colors when it paints, with a disabled item at 40 % opacity of the foreground; the system draws the menus on macOS); a button under the pointer has `toolbar.hoverBackground`, and the close button is `#e81123` as in VS Code, whatever the theme. The command center is a box in the middle of the bar with a search icon and the workspace name (`Anvil` while there is no folder), 24 px high, at most 450 px wide and 40 % of the bar, centered in the bar and moved aside for the menu bar and the buttons; it is left out when less than 120 px are free, and it replaces the window title, which the bar draws only while the command center is off. A click on it runs `workbench.action.showCommands`. It paints `commandCenter.background` when the theme sets it, a `commandCenter.border` or `commandCenter.inactiveBorder` line and `commandCenter.foreground` or `commandCenter.inactiveForeground` text, and the `commandCenter.active*` colors while the pointer is over it. The layout buttons, 28 px square before the window buttons, run `workbench.action.toggleSidebarVisibility` and `workbench.action.togglePanel` and show by their icon (`layout-sidebar-left` and `layout-panel`, with the `-off` icons while hidden) whether the part is shown. They are checkable buttons whose state the window sets from `Workbench::visibility_changed`, so they follow a part however it was shown or hidden, and a click alone changes nothing. Their tooltips and that of the command center name the key of the command and follow the key bindings. `window.commandCenter` and `workbench.layoutControl.enabled` turn the two off, and take effect while the window runs. The buttons are real buttons with accessible names (Minimize, Maximize or Restore, Close) that do not take the focus. The bar decides nothing about the window: a left press on the empty area (`move_requested`), a double click and each button are signals that `MainWindow` answers with `QWindow::startSystemMove()`, maximizing or restoring, `showMinimized()` and `close()`. The menu bar is the window's `QMenuBar`, not buttons that open menus: embedded in the bar it already opens a menu with Alt and its mnemonic, focuses the first menu on Alt alone, moves between menus and items with the arrow keys, opens the menu under the pointer while one is open, and collapses the menus that do not fit into its extension menu, and tests keep it so (Alt+R, the mnemonic of Run, is dropped, because the find bar uses it). The setting `window.titleBarStyle`, `custom` or `native`, is read from the settings file before the window is built, and `native` gives the window the system's frame and the menu bar below it; the other way of getting the system's frame is `ANVIL_NATIVE_FRAME`. `MainWindow` keeps the bar's title, active state and maximize icon in step with the window, and `MainWindow::menu_bar()` is the menu bar wherever it is: `QMainWindow::menuBar()` would make a new, empty one once the menu bar has been moved into the title bar.

`ui::WindowFrame` makes the outermost 5 px of such a window the resize handles. It is an event filter on the application, so it sees the mouse before the widget under it does: over a handle it shows the resize cursor (an override cursor, restored when the pointer leaves the handle or the window), and a left press there asks the window system for a resize with `QWindow::startSystemResize()` and goes no further. The handles are inside the window and no transparent margin surrounds it, because a margin outside the painted window gets no mouse input under WSLg. The filter sets mouse tracking on every widget of the window, including those added later, because a move without a button reaches only widgets that ask for it. Maximized and fullscreen windows have no handles. `ui::FrameBorder` draws a 1 px `titleBar.border` line around the window, over its children, so that the window's edge shows when the compositor draws no shadow. Fullscreen is the command `workbench.action.toggleFullScreen`, bound to F11 (Ctrl+Cmd+F on macOS) and in View ▸ Appearance ▸ Full Screen; it keeps a maximized window maximized when it ends. In fullscreen the title bar is hidden and shows while the pointer is within the top pixel of the window, and hides when it is more than a bar's height below. When the window system does not start a move or a resize (the offscreen platform, a window manager that ignores the request), `MainWindow::use_native_frame` gives the window the system's frame and moves the menu bar back into it. `MainWindowOptions::custom_title_bar` and the environment variable `ANVIL_NATIVE_FRAME` keep the system's frame from the start. The Windows snap layouts, the system menu and the shadow are [#144](https://github.com/djangbahevans/project-anvil/issues/144).

`ui::TabStrip` is the 35 px strip of tabs above the editor, painted by the widget itself on `editorGroupHeader.tabsBackground`, with a 1 px `editorGroupHeader.tabsBorder` line below it when the theme sets one. A tab shows its title in the UI font at 13 px, is at least 120 px wide and otherwise as wide as its title with 10 px before it and a 28 px area for the close button after it, and ends in a 1 px `tab.border`. The selected tab has `tab.activeBackground`, a line of `tab.activeBorderTop` on top and `tab.activeBorder` below it when the theme sets one; a tab under the mouse has `tab.hoverBackground` when the theme sets one. The close button is a 16 px cross, always on the selected tab and on another tab while the mouse is over it. A dirty tab shows a dot in its place that turns into the cross, on a `toolbar.hoverBackground` highlight, when the mouse is over the button. A click selects the tab when the button goes down, a click on the close button or a middle click anywhere on the tab asks to close it, and a drag moves the tab one place at a time as the mouse passes the middle of a neighbor. The context menu offers Close, Close Others, Close to the Right, Close Saved and Copy Path, and its actions find their tab by an identity that survives the other tabs moving while the menu is open. Tabs that do not fit scroll horizontally with the wheel, and the selected tab is kept in view. A drag that leaves the strip reports where the pointer is (`drag_out_moved`, `drag_out_dropped`) and changes nothing about the tabs; bringing the tab back over the strip, or pressing Escape, ends it without a drop, and the tab stays in its place, dimmed, meanwhile. The strip is a view of a model that `MainWindow` keeps in step: changing the model (`add_tab`, `remove_tab`, `set_tab`, `move_tab`, `set_current_index`) emits nothing, and only the user's actions emit signals. Setting a tab to what it already is does nothing, which keeps the cost of a keystroke independent of the number of tabs. The strip is a page tab list for assistive technology, with a page tab for each tab named by its title and described by its tooltip (and "Unsaved changes" while dirty), selected when it is the current one, with a press action that selects it and a close action that asks to close it; a retitled tab signals a name change and a change of selection signals a state change for both tabs involved.

`ui::codicons` (`codicons.hpp`) draws VS Code's icons by name from the Codicons font. The font, copied unchanged from the `@vscode/codicons` package of the pinned checkout, is a Qt resource and is registered with `QFontDatabase` the first time an icon is drawn, not at startup. A table in `codicon_table.hpp`, generated with the font by `scripts/generate-codicons.mjs` and ordered by name, maps each icon name to its code point; `codicon(name)` returns the character, and nothing for a name the table does not have. `codicon_icon(name, color, size)` draws the glyph into a `QIcon` for the normal, active and selected states, and at 40 % opacity for the disabled state; an unknown name gives a null icon. `split_label_with_icons` splits a label such as `$(sync~spin) Syncing` into text and icon segments with VS Code's marker syntax (a name of ASCII letters, digits and hyphens, an optional `~` modifier, and a backslash before a marker to show it as text), so that the status bar and the quick pick can draw labels with icons; modifiers are parsed and left to the caller. The font's `blank` icon is an empty glyph by design.

The icons of languages are those of the Seti file icon theme, VS Code's default. `scripts/generate-seti-icons.mjs` copies the font of the pinned checkout (`extensions/theme-seti`) into `resources/seti` with its notice and writes `seti_icon_table.hpp`, which gives each language id of the theme a glyph and a color for a dark theme and for a light one; CI checks that all three match the checkout. `ui::seti_icon(language id)` returns the theme's default file icon for a language that it does not name, and the font, a Qt resource, is registered the first time its family is asked for. The table follows the style sheet that VS Code makes of the theme: a definition with no color of its own takes that of the default file icon; a language with no light icon (`todo`) shows the light default one on a light theme; `jsonc` has the icon of `json`; and a high contrast light theme shows the dark icons, as VS Code applies the theme's light section to light themes only. A `QuickPickItem` can carry such an icon (`QuickPickIcon`: a font family and a glyph with its color for each of the two), which its row draws in a 16 px column before the label at one and a half times the size of the text. In a list where any item has one, the labels of the others are indented as far, so that they line up (VS Code indents only the rows that have an icon). Which of the two is drawn follows `WorkbenchColors::kind`, the kind of the applied theme. The icons that an extension names for its own languages (`contributes.languages[].icon`) are not shown.

`workbench::EditorLayout` (`src/workbench`, target `anvil::workbench`, no Qt) is the model of the editor area: groups of tabs and the tree that arranges them. A group has an id, its tabs in order (a tab is a document's URI, and a document is at most once in a group but can be in several groups) and the position of its active tab. The tree has groups as leaves and splitters as inner nodes; a splitter has an orientation (children side by side or one above the other), two or more children and a ratio for each, positive and adding up to one, and a child splitter always has the other orientation than its parent, so that every splitter is a real division of the space. The window starts with one empty group that has the focus.

The operations follow VS Code. Opening a document puts a new tab to the right of the active tab, or at the end, and activates it, or only activates the tab when the group has the document; `show` focuses the group that has the document (the focused one first) and otherwise opens it in the focused group. Each group keeps its tabs in the order they were active, and closing the active tab activates the one that was active before it (`workbench.editor.focusRecentEditorAfterClose`, on by default and an option of the model), or, with the option off, its right neighbor, or the left one when it was the last; a group that loses its last tab is closed unless it is the only group (`workbench.editor.closeEmptyGroups`, an option of the model). A tab moves within its group or to another group, where it becomes the active tab and the group gets the focus. Splitting a group in a direction adds a new group, empty or showing the active document, that takes half of the space of the group and gets the focus: a sibling in the splitter when its orientation matches the direction, otherwise a new splitter around the group. Closing a group gives its space to the sibling before it (after it for the first), collapses a splitter left with one child and merges a splitter into a parent of the same orientation; the focus moves to the group before it in the order shown, or after it for the first. Focus next and previous wrap around the groups in the order shown, left to right and top to bottom.

Every operation changes the model completely and then tells its observers, with `structure_changed` when the shape of the tree changed (a group was added or removed), `ratios_changed` when only ratios did, `tabs_changed` and `active_tab_changed` for groups that exist before and after, and `focus_changed`; a window reads the state of a group that is new. `find_inconsistency` names the first broken rule of the model (the tree shape, ratios, groups missing or repeated, a document twice in a group, an active tab out of range, a focus that does not exist), the tests call it after every step of random operation sequences that are compared with a naive reference, and loading a saved layout refuses one that breaks a rule. `to_json` and `from_json` save and restore the groups, tabs, active tabs, tree, ratios and focus.

`ui::EditorArea` builds the editor area from a `workbench::EditorLayout` and keeps it in step through the layout's observer: a `ui::Splitter` (the same sash as the parts of the window, with the `editorGroup.border` line) for each splitter of the tree, and a `ui::EditorGroupWidget` for each group, which holds the group's tab strip, find bar and editor. The area changes nothing in the layout except the ratios when the user moves a splitter; what the user does in a group (selecting, moving or closing a tab, typing, moving the caret, focusing) is a signal with the id of the group, and `MainWindow` answers by changing the layout, whose notifications change the widgets. A change of structure builds the splitters again and moves the existing group widgets into them, so a group keeps its state; the old splitters and the widgets of closed groups are deleted after the signal that led to the change has returned. Moving a focused widget between splitters takes the keyboard focus from it, so focus changes during the rebuild are ignored and the focus is put back on the focused group afterwards. A group without a tab hides its editor and find bar, and takes the keyboard focus itself. Dragging a tab out of its strip shows a picture of the tab at the pointer and, depending on what is under it, a line where the tab would go on the strip of another group, or a shade over the group (`editorGroup.dropBackground`): the whole editor for the middle of another group, half of it for the nearest quarter of an edge. Dropping reports it as `tab_dropped_on_strip` with the position among the tabs, `tab_dropped_on_group` or `tab_dropped_on_edge` with the direction, and the window moves the tab with `EditorLayout::move_tab`, after `split` for an edge, so the tab moves with its document and nothing is asked. A group that has only the dragged tab does not offer to split on its own edge, and the middle of the group the tab comes from is not a target.

`MainWindow` holds the open documents by URI (`documents_`), the layout, and the area, and everything that is about "the current document" is about the active tab of the focused group: the commands and menus (`view()`, `find_bar()` and `tab_strip()` are the focused group's), the window title, the cursor position in the status bar, and the extension host's active editor, which is told when the focused group's active document changes. A document is in at most one group in the window, because two groups showing it would need independent selections ([#18](https://github.com/djangbahevans/project-anvil/issues/18)): opening a file that is open in another group focuses its tab there, a split gives an empty group, and moving a tab to a group that has the document closes the moved one. Opening goes to the focused group, a new tab to the right of the active one. A group that loses its last tab closes unless it is the only one, and closing the last document of the window opens an untitled one in its place. Close Editor Group closes the focused group with its documents, asking about unsaved changes first, and does nothing for the only group. The tab strip of a group without the focus is painted with the unfocused tab colors.

## Settings

`core::parse_jsonc` reads JSON with comments and trailing commas and reports a syntax error with its line and column; the settings, keybinding and theme files share it. `core::Settings` holds the parsed object of the user settings file, finds a dotted key (`editor.fontSize`) whether the file writes it flat or nested, and keeps keys that nothing reads. `core::EditorSettings` reads the keys the editor uses with VS Code's defaults and ranges; per-platform defaults come from `platform::editor_defaults()` so that `core` has no per-OS code. A value of the wrong type is an error, not a silent default, so that a typo never changes the editor unnoticed. `core::parse_jsonc_tree` is the same parser with the position of every value and every property name: a `JsoncNode` has its kind and its byte range `[begin, end)` (counted from the start of the text, a byte order mark included), an object has its properties in the order of the text with the position of the comma after each, and an array its elements; a text fails in the same way and with the same message as with `parse_jsonc`. `core::edit_jsonc_property(text, key, value)` is the change of one setting in the text of a settings file for [0017](adr/0017-commands-change-settings-by-editing-the-file.md): it changes only the bytes of that setting and leaves comments, order, spacing, line endings and trailing commas alone. The property that holds the key is found in the order `Settings::find` uses (the key spelled flat, then a shorter prefix as an object that holds the rest, the last of a repeated name) and its value is replaced in place; a key that is not there is added as a flat property after the last property of the top-level object, indented like it, with a comma after the property before it (a trailing comma that the file uses is kept, a comment at the end of that line stays after the comma, and an object on one line gets the property on that line); a text of nothing but whitespace and comments gets an object after the comments. With no value the key is removed in every spelling: the property goes with its comma, and its line when it is alone on it, with a comment at the end of that line, and the comma of the property before it goes when the removed one was the last without a comma of its own. It fails with the position of the syntax error, or when the top level is not an object. The tests check each rule on the text it produces, and, on random files with comments, flat and nested keys, tabs, CRLF, trailing commas and objects on one line, that a replacement changes exactly the bytes of the value (the generator records where it wrote each), and that an addition or a removal only adds or takes out the characters of the property and its commas.

`MainWindow` decides the language of each document with a `core::LanguageRegistry` that it builds from VS Code's built-in languages, the `contributes.languages` that `exthost::read_contributions` reads from the manifests (in the order of the extensions, an entry with no `id` or a field of the wrong type being logged and skipped), and the user's `files.associations` (`core::read_file_associations`, which skips and reports entries whose value is not a language id; the entries come in the alphabetical order of their patterns). The registry is built again when the extension host starts or restarts and the associations are applied when they change; each time every open document is resolved again. The resolver that `DocumentsService` asks for a document that is registered without a language gets the resource (the file system path of a `file:` resource, the `path` of another) and the first line of the text; a document that an extension creates with a language keeps it (`language_is_fixed`) and the window leaves it alone when it resolves the others again. `DocumentsService::language_changed` tells the extension host of a change with `$acceptModelLanguageChanged`. The window keeps the language of each open document in a map that it fills when the document is first asked for, so that the status bar item on the right, left of the extension host's and right of the position, shows the name (the first alias, or the id) without asking the registry on every keystroke, and works without an extension host. A document that is saved under another name is registered again under it and is resolved by its new name. Change Language Mode (`workbench.action.editor.changeLanguageMode`, Ctrl+K M, a click on the status bar item) lists the named languages in the window's quick pick, which `pick_from` borrows from the command palette for the pick and which goes back to the palette's prefix, placeholder and handler the next time the palette opens: Auto Detect (for a document that has text), which drops the picked language and resolves the document again, then, for a `file:` document with an extension, an entry that asks for a language and writes `"*<extension>": "<id>"` to `files.associations` with `change_setting`, keeping the associations that are there (a dotfile is associated by its whole name, as VS Code does), then the separator `languages (identifier)`, and the languages by name, each with the icon of its language before it, its id in parentheses after the name as VS Code shows it and the current one marked "Configured Language". VS Code's entries for the settings of the language and for the Marketplace are not offered. The document is the one that was shown when the command ran, because the pick is not modal and the document can close or change name before an item is chosen. A picked language is kept in `chosen_languages_` for as long as the document is open: a change of the associations or of the extensions' languages does not touch it, Save As moves it to the new name and registers the document with it, an extension host restart registers the document with it, closing forgets it, and it is not written to the settings. The window disconnects the quick pick before the pick's widget is deleted, which closes it.

The comment tokens of a language, which Toggle Line Comment and Toggle Block Comment read, come from the `comments` of VS Code's language configuration files. `core::read_language_comments` reads one with VS Code's rules: `lineComment` is a string or an object with a string `comment` and an optional `noIndent`, and `blockComment` is an array of two strings; each kind is checked on its own, so a wrong `lineComment` leaves a right `blockComment`, an empty line token (which configurations use to say that a language has none) is no token and no problem, and an empty block token is a problem. `scripts/generate-language-comments.mjs` reads the configuration file that each built-in language contribution names, with the editor's own JSON parser, and writes `language_comments_table.hpp` (69 languages in VS Code 1.146); a configuration that sets a kind of token for a language that an earlier one already gave tokens replaces that kind, as `LanguageComments::overlaid_with` does, and a test reads the same files with the C++ reader and compares. `exthost::read_contributions` reads the `configuration` path of a language contribution, inside the extension's directory (a path outside is logged and skipped, as a theme's is), and `MainWindow::rebuild_language_comments` reads those files when it builds the language registry and lays them over the built-in tokens, so that an extension's configuration changes the kinds it sets and gives a language of its own tokens. A file that cannot be read or parsed is logged once and the language keeps what it had. `MainWindow::language_comments(language id)` answers the tokens of a language, or none.

Edit > Toggle Line Comment (`editor.action.commentLine`, Ctrl+/), Toggle Block Comment (`editor.action.blockComment`, Ctrl+Shift+A on Linux, Shift+Alt+A elsewhere), and the commands Add Line Comment and Remove Line Comment (`editor.action.addCommentLine`, Ctrl+K Ctrl+C; `editor.action.removeCommentLine`, Ctrl+K Ctrl+U) call `EditController::comment_lines` and `toggle_block_comment`, which port VS Code's `LineCommentCommand` and `BlockCommentCommand` with the tokens of the language of the document (`MainWindow::language_comments`). A toggle removes the tokens when every line that it touches has one and adds them otherwise, at the smallest indentation of the lines rounded down to a tab stop (`editor.tabSize`); a language whose configuration says `noIndent` gets the token in the first column; lines with nothing on them are left out unless `editor.comments.ignoreEmptyLines` is `false`, or unless they are all the lines there are; a space follows the token and goes inside a block comment unless `editor.comments.insertSpace` is `false`; the token is found whatever the case of its ASCII letters. A selection that ends at the start of a line leaves that line out. A language with a block comment and no line comment gets the block comment around the text of the lines, or the one that is there removed. With several selections the edits are one undo step, and the handling is VS Code's, quirks included: selections that share a line with the first selection comment it once, a selection that shares a line with a later one does not look at it and the line is commented once for each, a cursor whose edits overlap those of an earlier cursor is dropped, a selection that no edit touches keeps its line and column, and cursors that end up overlapping are merged into their union, in the direction of the cursor with the lower number unless the other one is the last one. A language with no token for the command changes nothing and the status bar says so (`Makefile has no block comment.`). `scripts/generate-comment-cases.mjs` runs VS Code's commands through its own editor machinery (the compiled `LineCommentCommand` and `BlockCommentCommand` with a test code editor, in Node with the CSS imports and the DOM stubbed) on 1600 generated texts, selections and options, and records the texts and selections they leave in `tests/core/data/comment_cases.json`, which `tests/core/comment_commands_test.cpp` replays against the port.

`ui::WatchedFile` tells that a file has changed: it watches the file and the nearest existing directory above it with `QFileSystemWatcher`, and sets both watches again after every change, so a file that is created later, deleted, or replaced by an editor that writes a temporary file and renames it is followed. Changes are debounced, so a save that touches the file several times is one `modified` signal. `ui::SettingsStore` reads `<user config dir>/settings.json` when told so. A file that cannot be used leaves the previous values in force and is reported once per distinct problem, through a signal that the window turns into a status bar message, and in the log. `ui::MainWindow` applies the values: `EditorView::apply_settings` takes the font, tab size and Tab key behavior and keeps the caret and the top visible line, the document service reports the tab size and `insertSpaces` to extensions, and new untitled documents take their line ending from `files.eol`. Applying settings happens when the file changes, never per keystroke. Auto save (`files.autoSave`, `files.autoSaveDelay`) lives in `MainWindow` and never touches a document that has no file: with `afterDelay` each change of a dirty document restarts its own single-shot timer (a map lookup per keystroke, whatever the number of tabs), and the timer saves the document if it is still dirty; `onFocusChange` saves the document of an `EditorView` that loses the focus to a widget outside its group (the find bar is part of the group), the document that another tab replaces in `refresh_current`, and every dirty document when the window is deactivated; `onWindowChange` saves only on deactivation. Turning auto save on, or changing its mode or delay, saves every dirty document with a file at once, as VS Code does. A failed automatic save is shown in the status bar and not in a dialog. `workbench.action.toggleAutoSave` switches between `off` and `afterDelay` through `change_setting`, and any other mode goes to `off`. The store writes the file only when a command asks for a change, with `SettingsStore::change(key, value)` ([0017](adr/0017-commands-change-settings-by-editing-the-file.md)), which `MainWindow::change_setting` wraps for commands: it reads the file, edits its text with `core::edit_jsonc_property`, reads the file again, and writes through `platform::write_file` only if the bytes are the ones that were edited, so comments and formatting stay. The new settings are in force at once with one `changed`, and the watcher's reload that follows reads the same settings and signals nothing. A missing file and its directory are created. When the file cannot take the change (there is no settings file, the text does not parse or does not validate with the change, a document of the window shows the file with unsaved changes (`MainWindow::has_unsaved_changes_in`), the file changed between the two reads, or it cannot be written), the file is left as it is and the change is made for this window only, in an override kept above what the file says: the overrides are applied as flat top-level keys, which `Settings::find` reads before a nested spelling, and they last until `change` is called for the same key again, which then writes the file and drops the override. A value that is not valid for its key is rejected and nothing changes. `change` returns which of the three happened and why, and `change_setting` puts the reason in the status bar ("Auto Save is changed for this session only: settings.json: line 4, column 5: ..."), or "was not changed" for a rejected value.

`ui::KeybindingsStore` reads `<user config dir>/keybindings.json` the same way, with the same reporting: a file that cannot be parsed, or whose value is not an array, leaves the previous bindings in force, and an entry that `core::read_keybindings` cannot use is left out while the others apply. A problem is reported once, with the first of them and the number of the others, until the file has been valid in between, through a signal that the window turns into a status bar message, and in the log. A reload that reads the same text as before changes nothing. `MainWindow` gives `KeybindingService` the default bindings followed by those of the user, so a user binding wins over a default one for the same key and a `-command` entry removes the default bindings of that command, and it does so at startup and on every change; the service ends a chord in progress when its bindings are replaced, and the menus take the new keys at once.

File > Preferences > Settings (`workbench.action.openSettings`, Ctrl+, or Cmd+,) and Keyboard Shortcuts (`workbench.action.openGlobalKeybindings`, Ctrl+K Ctrl+S) open `settings.json` and `keybindings.json` of the user's configuration directory in the editor, through `MainWindow::open_user_file`: a file that is missing is created first, with its directory, holding `{}` or `[]` and a line break, so that the file watchers have something to read and the editor something to edit; a file that exists is opened as it is, and one that is open already is shown by its tab. There is no settings editor with search and controls, so the JSON commands `workbench.action.openSettingsJson` and `workbench.action.openGlobalKeybindingsFile` run the same operation. Saving the file changes the running window through the file watchers above. A window that was started with no configuration directory says so in the status bar and opens nothing, and so does one whose file cannot be created.

The zoom of the window is the setting `window.zoomLevel`, a number from -8 to 8 (default 0, decimals allowed, a value outside the range is clamped) as in VS Code, whose window is scaled by `1.2` to the power of the level. View > Appearance > Zoom In, Zoom Out and Reset Zoom (`workbench.action.zoomIn`, `workbench.action.zoomOut`, `workbench.action.zoomReset`, Ctrl+=, Ctrl+- and Ctrl+NumPad0, with Ctrl+Shift+=, Ctrl+NumPad_Add and Ctrl+NumPad_Subtract as the other keys of VS Code and Cmd for Ctrl on macOS) write the setting through `MainWindow::change_setting`, so that the level is kept in the settings file and is read again at the next start (VS Code does the same with `window.zoomPerWindow` set to `false`); Zoom In and Zoom Out first round the level to a whole number, as JavaScript's `Math.round` does, and do nothing when the result leaves the range. A change of the setting, by a command or by editing the file, reaches `ui::Zoom`, which `MainWindow` owns, through `MainWindow::apply_settings`: `Zoom::scaled(size)` is a size in pixels times `core::zoom_factor(level)`, rounded and at least 1 for a size above 0 (`core::scale_for_zoom`), and `Zoom::changed` is emitted when the level changes, so that a part that lays itself out from `scaled` does it again without being recreated. The editor text follows through the settings that every view receives: the pixel size of the font is `editor.fontSize` scaled by the level, and the line height, the character width and the scroll bars follow from the font, with the first visible line kept in view. The bars follow it too: `TabStrip`, `StatusBar`, `ActivityBar` (with the width of its column in `Workbench`) and `TitleBar` are given the `Zoom` (`set_zoom`; `EditorArea::set_zoom` and `Sidebar::set_zoom` pass it on to the strips and the activity bar, including the strips of groups made later) and read each fixed size through it: the height, the font, the paddings, the minimum width of a tab, the close button and its cross, the dot, the item margins of the status bar, the buttons, icons and indicator of the activity bar, and the title bar's height, window buttons, layout buttons, command center and menu bar font. The `constexpr` sizes that tests read (`TabStrip::height_pixels`, `StatusBar::height_pixels`, `Workbench::activity_bar_width`, `TitleBar::bar_height`) are the sizes at level 0, and the accessors of a part (`TabStrip::strip_height()`, `StatusBar::bar_height()`) give the size now. A part lays itself out again on `Zoom::changed` without being recreated, and the layout around it follows from its fixed height or width. A Codicon icon (`codicon_icon`) draws its glyph at the size it is asked for, so that the icons of the activity bar stay sharp at any level. The rest of the window follows in the same way: the title of the side bar, the header, tabs and buttons of the panel, the find bar (its font, margins and spacing), the quick pick and the command palette (the rows, the paddings, the input, the shadow, the maximum width and the font), the menus (`MenuStyle`: item and separator heights, the label, check and shortcut columns, the glyphs, and the font that `MainWindow::menu_font` gives each menu and the menu bar of a window with the system's frame), the Explorer (rows, indentation, twisties, paddings, font), the sashes of the splitters, the scroll bars of the editor, the quick pick and the Explorer, the paddings of the editor's text and line numbers, and the picture of a dragged tab. `Workbench` gives the sidebar, the panel and the editor area their minimum sizes at the zoom, no more than the window has room for when a part's minimum has grown beyond what the window can hold (half of the room that is left beside the activity bar and the sashes, or below the title bar and above the status bar, though never under the minimum of level 0), so that a window at level 8 still lays out inside itself. A change of the level keeps each part at the size it has, to its new minimum at least, and a part that has never been resized starts at the scaled default size when it is first shown. A widget that has a font of its own that a parent's font does not reach (a push button, a line edit) gets the scaled font set on it. A part takes the `Zoom` through `set_zoom`, or reads it from the `Workbench` that it fills (`Sidebar`, `Panel`), and reads every size in pixels through `Zoom::scaled`, `scaled_by` or a function of the part that does; `ZoomSourcesTest` reads the sources of `src/ui` and fails for a `constexpr` number or a call that gives a size in pixels (`setFixedHeight`, `setPixelSize`, `setMinimumWidth` and the like) that is neither scaled nor listed with the reason, so a new part cannot start with a size that stays at level 0.

Settings are global. Per-language overrides (`"[python]": {...}`), workspace settings and a settings editor are not implemented; the parsed JSON keeps its nesting so that they can be added.

## Files

`platform` reads and writes whole files (`file.hpp`: `read_file`, `read_file_range`, and `write_file`, which writes a temporary file and renames it over the target) and, in `file_system.hpp`, inspects and changes the file system for the file system service of the extension host: `stat_path` (the type as VS Code's bit flags, with the symbolic link bit added to the type of the target and alone for a broken link; the size; the modification and creation times in milliseconds, the creation time from `statx` on Linux and `st_birthtime` on macOS or the creation time on Windows, and the modification time where the system records none; whether the owner cannot write), `list_directory` (entries sorted by name, as bytes that need not be UTF-8), `make_directory` (with its parents), `remove_path`, `rename_path` and `copy_path`. A symbolic link is removed and copied as a link and never followed out of a tree that is removed. An existing target stops a rename or a copy unless `overwrite` is set, and is then removed first when it cannot be replaced directly; a target that contains the source and a directory copied into itself are refused before anything is removed. A move to another file system fails. The failures that callers tell apart are `ErrorCode` values (`not_found`, `already_exists`, `not_a_directory`, `is_a_directory`, `permission_denied`), and the rest are `io_error`. The portable parts use `std::filesystem`; only the times are per OS (`file_times_<os>.cpp`), and the macOS and Windows ones have not been built.

`exthost::FileSystemService` serves `vscode.workspace.fs` for `file:` resources with these operations; the Node extension host serves most `file:` calls itself, so the editor sees rename, copy, deletes that use the trash and other schemes (see the protocol reference).

`platform::FileWatcher` reports the files and directories that are created, changed and deleted below a path (`file_watcher.hpp`). A worker thread reads the operating system's events and the owner takes them with `poll(timeout)` from its own event loop, so the interface has no Qt and no callbacks on another thread. Events of a burst for one path are merged into one and delivered together once no event has come for `latency` (50 ms) or `max_delay` (500 ms) after the first: a created path that changes stays created, a created path that is deleted is not reported, a changed path that is deleted is deleted, and a deleted path that is created again is changed. A rename is a deleted old path and a created new path, and a directory that appears or is moved in is reported with everything in it. A watcher that is not recursive can watch more single directories than the one it started on (`add_directory` and `remove_directory`, under a mutex shared with the worker), so that a view of a folder follows the directories it has open with one thread and one inotify instance. Paths that match the exclude globs (`core::glob_match`: `*`, `?`, `**` as a segment, `[a-z]`, `{a,b}`, matched against the path below the watched one) are not reported and an excluded directory is not watched, which keeps `node_modules` out of the system's watch limit. The Linux implementation uses inotify with one watch per directory. `start` watches the path itself and returns: the directories below it of a recursive watch are added by the worker thread, breadth first, a few milliseconds at a time between the events it reads and a request to stop, so that starting a watch of a large folder does not wait for the tree (10,100 directories take about 170 ms in the Debug preset, and a folder of tens of thousands of directories seconds, cold). `ready()` says when every directory that existed at the start is watched, and a change in a directory that has no watch yet is not reported. The worker adds the watch of a new directory before it reads what the directory holds so that nothing is missed, ends the watches of a directory that is moved out or deleted, and reports reaching `fs.inotify.max_user_watches` as `limit_exceeded`, from `start` when not even the path itself fits and otherwise from the next `poll` once, while the watch goes on with the directories it has; the same goes for a directory that cannot be watched and for a queue overflow that loses events. `WatchOptions::max_directories` sets a limit of the watcher's own. Windows ([#201](https://github.com/djangbahevans/project-anvil/issues/201)) and macOS ([#202](https://github.com/djangbahevans/project-anvil/issues/202)) have stubs that fail with `unsupported`.

`exthost::FileEventService` serves `workspace.createFileSystemWatcher` with these watchers: `$watch` starts a `platform::FileWatcher` for a `file:` folder (or shares the watcher of an earlier watch that covers it), `$unwatch` ends it, and `ExtensionHost::pump` sends the events of each watcher as `$onFileEvent` batches. The service also watches the workspace folder, because the extension host relies on the editor for that (see the protocol reference); a watch that cannot start, because the folder does not exist or the system's watch limit is reached, is logged and the others go on, and a limit that is reached while the directories of a watch are being added is logged from `poll` and leaves the watch with the directories it has. Neither the workspace watch when the host starts nor a `$watch` waits for the directories of a large folder to be watched (`FileEventService::ready` tells when all are), so opening a folder with many thousands of directories does not stall the window. Watchers stop with the host.

`exthost::ActivationService` fires activation events (`ExtensionHost::fire_activation_event`) and tells the caller when the extensions have activated. An event waits until the startup sequence has sent the workspace, in order, because the extension host cannot answer before that and an extension that activates at startup may wait for the event. `CommandsService` fires `onCommand:<id>` through it, `DocumentsService` fires `onLanguage:<id>` and `onLanguage` for the first document that has a language, and `FileSystemService` fires `onFileSystem:<scheme>` before an operation on a resource whose scheme is not `file` and replies, once the activation has finished, as for a scheme without a provider. The protocol reference lists which events fire, and by whom.

`exthost::FileSystemProviders` keeps the file systems that extensions provide for their own schemes (`workspace.registerFileSystemProvider`) by scheme, and calls them in the extension host: `stat`, `read_directory`, `read_file`, `write_file`, `rename`, `copy`, `create_directory` and `remove` take a resource and call back with the result or a provider error code, which is what the editor itself uses to read and write such a resource (documents of such schemes are [#213](https://github.com/djangbahevans/project-anvil/issues/213)). `FileSystemService` serves the requests of `MainThreadFileSystem` on resources of such a scheme with it, after the `onFileSystem` activation, and `FileEventService` sends the changes that a provider reports as file events and passes watches of its resources to it. A provider that registered as read-only is never asked to change anything. `Session::call_binary` sends arguments that are buffers and gives the buffer of a reply. The tests of the provider calls use `FakeHost`, and a fixture extension with an in-memory file system and a read-only one against the real extension host.

`core::Workspace` is the folder the window works on: its canonical path, its name, and a stable id made by a fixed hash of the path (see the protocol reference, "Workspace"), by which extension storage is kept per workspace. `core::parse_launch_arguments` turns the command line into the optional workspace, the files to open and the problems to report: the first directory is the workspace, and a second directory or a missing folder (an argument that ends in a separator) is reported and ignored. `MainWindowOptions::workspace` shows the folder's name in the window title and the command center, and `ExtensionHostBridge::Config::workspace` reaches the extension host as the init data's workspace and the `$initializeWorkspace` call. File > Open Folder… (`workbench.action.files.openFolder`) and Close Folder (`workbench.action.closeFolder`) change the workspace of the running window by restarting the extension host ([0016](adr/0016-opening-a-folder-restarts-the-extension-host.md)). `MainWindow::open_folder` and `close_folder` set `MainWindowOptions::workspace`, and `ExtensionHostBridge::restart` stops the running host and starts another with the configuration of the first and the new workspace; it also starts a host that stopped for another reason. Requests that the old host has not answered fail with "the extension host restarted" (`ExtensionHost::abandon`, `Session::fail_pending_calls`). The window keeps its tabs, groups and documents, including unsaved ones, and asks nothing: it registers its documents with the new host before the event loop runs, so that they are in the host's first documents delta, makes the editor of the shown document, shares its commands again, and reads the key bindings and themes of the extensions again, listing a theme once. The commands only schedule the restart: they run inside the host that the restart destroys, since every command goes through the host while it runs. `MainWindowOptions::choose_folder` replaces the folder dialog, which tests use; cancelling the dialog changes nothing, and opening the folder that is the workspace does nothing. The context key `workbenchState` is `folder` while a workspace is open, which shows Close Folder in the menu.

`core::FileTree` is the model of the explorer: the directories of the workspace folder that have been read, with no Qt and no OS code. It is built from the root and a `DirectoryLister`, a function that lists one directory as entries with a name, whether it is a directory and whether it is a symbolic link, or fails with an `Error`. The lister keeps `core` free of OS code: `ui::ExplorerModel` backs it with `platform::list_directory`, and the tests use a counting fake. `children(path)` lists a directory the first time it is asked for and returns the same entries afterwards, so a directory the user never opens is never read; `refresh(path)` lists a loaded directory again and returns the entries that were added, removed or changed (a file that became a directory or the other way round, or whose symbolic link flag differs), in the order of the tree, and forgets what had been loaded below a removed or changed entry so that a new directory of the same name is read afresh. A path outside the root, an excluded path and one below an excluded directory have no children and are not listed. A symbolic link to a directory is a directory entry that the tree does not follow by itself, so a link loop is as deep as the user opens it. A directory that cannot be listed has no entries and keeps its `Error` (`error(path)`) until the next `refresh`; the rest of the tree is unaffected. The reading itself is done by `DirectoryReader` (`FileTree::reader()`), which lists, leaves out the excluded entries and sorts from copies of the lister and of the patterns, so that a worker thread can read a directory while the tree changes (the lister must be callable from that thread); it gives nothing when its `std::stop_token` was requested, which it looks at after the listing and before the sort. `FileTree::adopt` takes the listing of a reader as if `children` had made it, and `forget` drops a directory and what is below it so that the next `children` lists it again. `refresh` compares the old and the new entries by name in one pass, which keeps it linear for a directory of tens of thousands of entries. Entries are ordered as the explorer of VS Code does: directories first, then each group by `core::compare_file_names`. `FileExcludes` holds the patterns of `files.exclude` (`set_excludes` replaces them, and the next `refresh` of a directory applies them), matched with `glob_match` against the path relative to the root with forward slashes; the defaults are `**/.git`, `**/.svn`, `**/.hg`, `**/.jj`, `**/.DS_Store` and `**/Thumbs.db`, and `FileExcludes::from_setting` reads the setting's object, turning a pattern off for `false` and reporting a value that is an object (a `when` condition, which is not supported) or neither boolean as a problem.

`core::compare_file_names` is `compareFileNamesDefault` of VS Code, which is an `Intl.Collator` with `numeric: true` followed by the shorter name first for names the collator treats as equal (`a1` and `a01`). The port reproduces the root collation of ICU for the characters that file names mostly hold: digit runs compare as numbers; whitespace, punctuation and symbols sort before digits, digits before letters, in ICU's order for ASCII (`_ - , ; : ! ? . ' " ( ) [ ] { } @ * / \ & # % ` ^ + < = > | ~ $`); letters ignore case and accents first, then differ by accent (acute, grave, circumflex, ring, diaeresis, tilde, cedilla, stroke), then by case with the lower case first; the Latin-1 letters with a diacritic sort with their base letter, `æ` and `ß` as `ae` and `ss`; Greek and Cyrillic capitals fold to their lower case; other characters sort after the letters by code point, which is not ICU's order between scripts; control characters are ignored. A final tie is broken by the bytes, so only identical names compare equal. `FileNameKey` computes the keys of a name once, which the tree uses to sort a directory without decoding names on every comparison. `tests/core/data/file_name_order_cases.json` holds the order that VS Code's own comparer gives for a corpus of names (numbers, case, accents, punctuation, dots, other scripts), recorded by `scripts/generate-file-name-order-cases.mjs`, and the tests check every pair.

`exthost::DocumentsService` applies a `WorkspaceEdit` that creates, renames and deletes files (`$tryApplyWorkspaceEdit`; the rules for each option and the replies are in the protocol reference). `exthost::parse_file_operation` reads the file operations of the edit, `FileOperationPlanner` checks the preconditions of the whole edit in order before anything changes, and `perform` runs one operation and returns how to take it back. The service runs the edit as steps, each a file operation or the text edits between two of them, and keeps the undo actions of the steps done, which a failing step runs in reverse; the text edits of a step are undone with the undo of their document. What happens to an open document follows the file. A rename registers the same `core::Document`, with its text, selections and undo history, under the new URI (`DocumentsService::rekey`), for a file or for each document below a renamed directory, and keeps its editor; the observer's `renamed` callback reaches `MainWindow::document_renamed`, which moves the tabs, the language, the highlighter and the navigation history to the new URI as Save As does (`rekey_document`), so a tab keeps its place, its undo history and its unsaved changes under the new name. A deleted file's document without unsaved changes is removed and the observer's `deleted` callback makes `MainWindow::document_deleted` close its tab in every group without asking, leaving an untitled document when it was the last one. A document with unsaved changes is neither removed nor closed, so that no text is lost, and saving it writes the file again. An edit that would put a created file or a renamed file over a document with unsaved changes is refused. A document that is replaced by a file that overwrites it, without unsaved changes, is closed like a deleted one.

## File search

The files of a folder are listed when something asks for them, by ripgrep, and nothing indexes or watches them ([0020](adr/0020-listing-workspace-files.md)). `search::find_ripgrep` takes `ANVIL_RG` as it is given, else the binary that the VS Code checkout carries for the platform, else `rg` in an absolute directory of `PATH`. `core::FileSearchOptions` reads what to leave out from the settings: `files.exclude` with `search.exclude` over it, and the switches for ignore files and symbolic links, with VS Code's defaults. `search::list_arguments` passes them as VS Code does, and `search::FileListing` runs `rg --files` in the folder and gives the paths in batches as they arrive, each the bytes of its name. A listing has no thread: its owner reads it with a timeout, from a worker or from an event loop, and destroying or cancelling it ends ripgrep. Status 1 is a folder without files; any other failure is reported with the start of what ripgrep wrote to standard error, and the files that arrived are good. A listing can be narrowed to the files that include globs match. `exthost::WorkspaceService` answers `workspaceContains:<glob>` activation that way: it polls its listings from the host's pump without waiting, replies at the first file, and ends ripgrep with the answer, after 5 s or with the host ([protocol](extension-host-protocol.md#activation-events)).

## Extension compatibility

The upstream extension host runs unmodified from a pinned VS Code release. The editor answers its RPC calls for the in-scope API surface and reports unsupported API use explicitly. Extensions are installed from Open VSX or from local `.vsix` files ([0007](adr/0007-extension-registry-open-vsx.md)).
